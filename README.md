## これは何？

『**yomiyasu（よみやす）**』は、AIが生成した日本語の不自然な比喩、曖昧な主述関係、不要な装飾を直し、読みやすい文章に整えるスキルです。

主に技術記事、設計書・仕様書、PR説明文、社内レポートなどの実務的な文章を対象として設計されています。

Claude Code、Codex、CursorをはじめとするAIコーディング環境に読み込ませて使用してください。

2.0.0-beta からは、推敲の前と後を比べる検査をまとめて実行し、その記録を残すスクリプト（`yomiyasu_check.py`）を同梱しています。検査の実行漏れと、数値・否定などの変化を見つけやすくなりました。検査が出すのは見直し候補で、意味が保たれたことや読みやすさの合格を示すものではありません。2.0.0-beta は先行版です。このバージョンのスキルを実際に動かして確かめたのは Claude Code だけで、確かめた範囲は[限界](#限界)の節に書いています。

## 背景と課題

AIによる文章生成は日常的な道具となりました。
一方で、AIで生成された文章には独特のクセが残りやすく、そのままでは実務や技術発信に使いにくい場面が多くあります。

これまでに様々な文体調整プロンプトやスキルが試みられてきましたが、依然として「AI特有の読みにくさ」が残るケースが見られます。

従来のアプローチが抱えていた限界は、主に次の4点でした。

1. 禁止語の置き換えにとどまる対処
   手触りや解像度、泥臭いといった表層の単語を禁止しても、別の曖昧な語へ置き換わるだけで、不自然な文構造そのものは解消されませんでした。
2. 編集ルールの過剰適用
   修辞規範を過度に与えると、モデルが指示を過剰に解釈し、かえって不自然な造語や大げさな文体を招いていました。
3. 主述関係の曖昧さと非生物主語
   誰が何をどうするのかが省略されたまま、概念や道具が比喩的な動詞（壊れる、倒す、効くなど）と結びつき、読み手側で過剰な文脈補完が必要でした。
4. 形式の偏重と情報密度の低下
   太字や箇条書きが増加する一方で、手順やコードの仕組みといった核心部分が抽象化され、文章量に対して実質的な情報が希薄化していました。


## 本スキルのアプローチ

元の意味を保ち、読み違いや文の関係を追う負担がある箇所を直します。自然に読める部分は残します。

### 7つの変換原則

1. 主述・修飾・条件の点検
   主語と述語、修飾語と掛かる先、指示語と指す対象を対応づけます。条件・例外・否定・並列・数量・順序も、書き直す前後で同じように追えるか確かめます。主体や対象を補うのは、原文や提供文脈から確定できる範囲に限ります。
2. 文の働きと文体の保持
   文ごとの説明・依頼・助言・予定を区別し、働きに合わない文末だけを直します。完了した変更作業、現在の動作や方針、今後の予定を時制と役割に合わせて書き分け、語尾を散らすこと自体を目的にしません。変更指定がない常体・敬体は保ち、技術記事という分野だけで敬体へ変えません。
3. 擬人化の整理
   道具や概念に感情や意志を持たせた表現を直します。道具やシステムの客観的な動作を述べる非生物主語は残します。
4. 比喩を平易な言葉へ
   `壊れる`、`倒す`、`効く`、`溶かす`などを、元の含みや意味の広さを保って言い換えます。動詞を替えた後も、主体・対象・修飾先を変えず、語順を追いやすくできるか確かめます。
5. 前置き・否定対比の役割の確認
   前置きを削るのは、削っても主張や比重が変わらない場合だけです。評価や必要な対比、比較から方針へ移る接続は残します。
6. 情報を勝手に足さない
   主張・比重・言い切りの強さ・文の働きを保ち、原文にない主体・原因・条件・数値・感情などを足しません。ルールを「契約」、比較の基準を「正本」と大げさに呼ぶ場合は役割に合う語へ直し、文字どおりの意味や定義済みの専門用語は保ちます。意味を確定できない箇所は、原文にある未確定の状態や既知の動作を本文に残した暫定文とし、推敲理由や確認事項は読者向け本文中ではなく本文の後に添えます。
7. 文長・読点・装飾の調整
   平均文長30〜45文字、1文の読点0〜2個を目安にします。読みやすい原文の読点を、数や見た目だけで削りません。不要な文末コロンと、ラベルと値の対応を示すコロンを区別します。過剰な装飾記号を整理し、英単語や数値の前後の空白は元の書式や指定されたスタイルを保ちます。残す太字は表示される形に整えます。

### 2.0.0-beta で足した手順

書き直す前に、文書の種類（PR説明、障害報告、エッセイ・小説、紹介記事・宣伝文、メール・チャット、論文・研究レポートなど12種類）と読者の知識（3段階）を決め、種類に合わせて当てない規則を変えます（[使い方](#文書の種類と読者の指定)の節）。

規則に当たった箇所は、直す前に案と原文を6点（何について述べるか、何を認め何を否定するか、誰が誰にするか、範囲と条件、言い切りの強さ、数値・固有名詞・時期）で比べます。1つでも変わるなら原文を残し、完了報告の「残したAIっぽいところ」に書きます（言い直しテスト）。

書き直したあとは、付属の `yomiyasu_check.py` で lint と diff をまとめて実行し、提出の直前に、最終稿が検査したものと同じかを記録と照らします（[付属ツール](#付属ツール)の節）。


## Before → After 例

次の2つの例は、SKILL.md を組み直したあとの 2.0.0-beta のスキルを Claude Code（Claude Opus 5.5）で1回ずつ動かした最初の出力です。よい回を選び直してはいません。組み直したあとのスキルで前に作った例2は、原文にない「確実に」を足していました。そこで SKILL.md に、言い換えるときに原文より強い確度や程度の語を足さない、という1文を足し、2つの例を作り直しています。この1文は、例2の「地味に」の言い換えを見て書いたもので、「地味に」の含みを「目立たないながらも」のような言い方で表す例を含みます（`references/gemini-syntax.md` にも同じ言い換えの例があります）。作り直した例2に「確実に」が出なかったことは、この例に合わせて直した結果で、ほかの文章での効き目を示すものではありません。Before は 1.1.2 までの README と同じ文で、どちらも AI が書いた文章です（例1はデジタル庁の資料をもとに、例2は AI が書いたとみられる設計メモをもとに書かせたもの。`evals/comparison_benchmark.md` のセット A と B を短くしたもの）。After は最終稿そのままです。例ごとの最後の行は、スキルの実行とは別に、その最終稿を `yomiyasu_check.py` の run と verify（`--replay` 付き）に通し直したときの状態の行です。

スキルが推敲の中で残した記録では、2つの例とも、1回目の検査で意味が変わる恐れは0件でした。どちらも、検査のあとに本文を直さずに提出しています。提出前の verify は、2つとも `--replay` なしでした。

After の変化は、1.1.2 までの README の After より小さくなっています。原文だけでは意味を決められない箇所（例1の「片方」「もう片方」、例2の2行目と「この境界線」）は、説明を作り足さずに残し、書き手に確かめる点として報告しています。原文の最後にあった定型の結びは、例1では残り、例2では消えました。確かめに使った2つのモデルは、どちらの After にも確かな意味の変化を挙げませんでした。詳しくは[例について確かめたこと](#例について確かめたこと)に書きました。

### 例2: 技術解説

#### Before
> 非同期処理における**最大の落とし穴**は、ネットワークの瞬断です。
> 
> **依存構造は分割できない。動かしながら引き返す。**
> 
> 単にメッセージを流すだけでは、背後でデータが**静かに壊れます**。前提を、経路が代わりに添えてくれるわけではありません。
> 
> そこで**地味に効いてくる**のが、以下の3つの原則です。
> - **冪等性の担保**: 重複した処理は**黙ってスキップ**します。
> - **安全なリトライ**: 指数バックオフを挟むことで、DBの負荷を逃がします。
> - **DLQへの退避**: 破綻したメッセージは隔離し、原因を1つずつ**潰していきます**。
> 
> デバッグで丸一日**時間を溶かさない**ためにも、この境界線を意識した設計が不可欠です。いかがでしたでしょうか。

#### After
> 非同期処理における最大の落とし穴は、ネットワークの瞬断です。
> 
> 依存構造は分割できません。動かしながら引き返します。
> 
> 単にメッセージを流すだけでは、気づかないうちにデータがおかしくなります。経路が前提を代わりに添えてくれるわけではありません。
> 
> そこで、目立たないながらも役立つのが次の3つの原則です。
> - 冪等性の担保: 重複した処理は知らせずにスキップします。
> - 安全なリトライ: 指数バックオフを挟むことで、DBの負荷を逃がします。
> - DLQへの退避: 破綻したメッセージは隔離し、原因を1つずつ取り除いていきます。
> 
> デバッグで丸一日を無駄にしないためにも、この境界線を意識した設計が不可欠です。

#### 変更説明
太字を10か所すべて外しました。2行目の「依存構造は分割できない。動かしながら引き返す。」は、太字を外し、ほかの文に合わせて「です・ます」にそろえています。比喩は、「背後でデータが静かに壊れます」を「気づかないうちにデータがおかしくなります」に、「地味に効いてくる」を「目立たないながらも役立つ」に直しました。前の出力のような「確実に」は足していません。「黙ってスキップします」は「知らせずにスキップします」に、「潰していきます」は「取り除いていきます」に、「時間を溶かさない」は「丸一日を無駄にしない」に、「以下の3つ」は「次の3つ」にしています。結びの「いかがでしたでしょうか。」は消えています。スキルは、何も伝えていない定型の結びとして消したと報告しています。

箇条書きは、ラベル、コロン、順番を残し、ラベルの太字だけを外しました。「冪等性の担保」のような名詞のラベルと、「DBの負荷を逃がします」は、そのまま残っています。「知らせずに」は、SKILL.md が「黙って」の直し方として挙げる「気づかないうちに」より、通知を出さないという仕組みの側に寄った言い方です。「前提を、経路が代わりに添えてくれる」は、語順を「経路が前提を」に変えただけです。何をどう添えるのかが分かりにくい比喩ですが、言い換えてはおらず、書き手に確かめる点にも入っていません。2行目の「動かしながら引き返します」が何をすることかと、「この境界線」が何を指すかは、書き手に確かめる点として報告しました。lint は、2行目の「引き返す」の1件を、比喩動詞の候補として warn で出します。

```text
yomiyasu-check: executed via=verify run=20261015T011848Z-d9c73196 attempt=1 final=sha256:4ebfe382e1b6 mode=rewrite doc_type=article checks=lint,diff meaning_risk=0 replay=ok
```

### 例について確かめたこと

2つの After のどちらにも、主張の逆転はありません。例1の「単なるパーツの共通化ではなく」は否定のまま残り、目的の側に回っていません。原文と After は、2つのモデル（Claude と Gemini 4 Argon）にも判定させました。モデルの判定は参考です。

例1は、2つのモデルとも意味を保ったとし、意味が変わった箇所を挙げませんでした。例2は、Gemini 4 Argon が意味を保ったとし、Claude は「少し変わった」として、「静かに壊れます」を「おかしくなります」とした箇所を挙げました。データ破損の深刻さが弱く読めるかもしれない、という理由です。確かな意味の変化は、どちらのモデルも挙げていません。`yomiyasu_check.py` の diff も、2つとも意味が変わる恐れを0件としています。例2で結びが消えたことは、どちらのモデルも意味の変化に挙げず、適切な直しとしています。Gemini 4 Argon は、例2で短い言い切りや話し言葉の弾みがすべて平らな言い方に替わり、記事の勢いが落ちたとしました。Claude は、技術記事なので落としてよい直しとみています。

1.1.2 までの README に載せていた After は、lint の見直し候補が0件でした。しかし、原文にない内容（例1の「高品質な行政サービス」、例2の「サーバーの再起動」）を足し、例1では否定していた「パーツの共通化」を目的の側に回していました。同じ After を 2.0.0-beta の diff に通すと、例1で意味が変わる恐れが3件（否定対比の主張の逆転、消えた数値「3点」、文の種類の印）、例2で1件（消えた数値「3つ」）出ます。「サーバー」「再起動」は「元の文にない語」に出ますが、意味が変わる恐れには出ません。lint の候補が0件でも、意味が保たれたとは限りません。

## 使い方

AIチャットやコーディングエージェントに対して、下書きを貼り付けて次のように指示します。

```text
この文章を読みやすくして。
（ここに修正したい文章を貼り付け）
```

### 文書の種類と読者の指定

文書の種類と読者は、依頼の中で伝えられます。伝えなければ、スキルが行き先と本文の形から推定します。推定に自信がなく、答えによって直し方が変わり、問い返せる場面では、書き直す前に1回だけ確かめます。本文だけを返す指定、一回きりの実行、ほかのスキルの途中、「質問しないで」と頼まれたときは確かめず、種類を決めないまま、種類ごとの規則を当てずに直します。

```text
この障害報告を、専門知識のない社外の利用者向けに読みやすくして。
（ここに修正したい文章を貼り付け）
```

種類ごとに、その種類で普通な書き方には当てない規則があります。値は付属ツールの `--doc-type` と同じです。

| 値 | 種類 | 当てない規則 |
|---|---|---|
| pr | PR説明 | 過剰な箇条書き（変更点、確認したこと） |
| article | 技術記事 | なし |
| incident | 障害報告 | 過剰な箇条書き（時系列）、硬い漢語（発生、復旧などの報告の語） |
| proposal | 提案書 | なし |
| minutes | 議事録 | 過剰な箇条書き（太字のラベルを含む）、同じ文末の連続（〜しました。の連続）、伝聞の「〜とのこと」 |
| manual | マニュアル | 過剰な箇条書き（番号つきの手順） |
| slides | スライド | 過剰な箇条書き（太字のラベルを含む）、数の宣言、繰り返すだけの「まとめ」、体言止めの項目での主語の抜けと文末 |
| essay | エッセイ・小説 | 読み取れる比喩（エッセイでも「効く」の類は直す）、小説のコピー調とダッシュ |
| formal | 公用文、規程、契約書、仕様書 | 硬い漢語（正式な語）、「〜を行う」「〜することができる」の外枠 |
| promo | 紹介記事・宣伝文 | 見出しのキャッチコピー、「！」と絵文字、勢いのある語と強める語 |
| mail | メール・チャット | 宛名、挨拶、結び、署名、クッション言葉の削り、敬語の度合いと口語の書き換え、絵文字の削除 |
| paper | 論文・研究レポート | ぼかした語の具体化（慎重な言い方）、専門用語と論文調（本研究では）の言い換え、長い文の分割、名詞化の言い換え |

エッセイ・小説では、何を何に例えたかが読み取れる比喩を書き手の個性として残し、主語と述語が成り立たず連想もできない比喩を直します。紹介記事・宣伝文では、「！」（同じ段落に3つ以上あっても）、評価の語を短く重ねる型（安い。うまい。早い。）、同じ褒め言葉の繰り返しを残し、根拠のない誇張は書き換えずに書き手へ根拠を尋ねます。どちらも、書き手の表現を残したときは、そう判断したことを本文とは別に1行で伝えます。

メール・チャットで残すのは、宛名、挨拶、結び、署名、クッション言葉、敬語の度合い、チャットの口語で、直すのは敬語の誤りなどです。論文・研究レポートでは、慎重な言い方を断定に変えず、引用の印、数値、専門用語、「である」調を残します。

読者は3段階です。expert（同じ分野の専門家）には用語を残して説明を足しません。informed（分野は違うが技術に詳しい人）と general（専門知識のない人）では、原文と資料にある説明で言い換えるか添えます。説明が原文と資料にないときは、説明を作らずに語を残し、「ここに説明が必要です」と書き手に返します。見出しと節の数と順は、どの種類と読者でも変えません。

種類を決めないときは、種類ごとの規則を当てず、1.1.2 からある分野別の指針（技術記事 tech、業務文書 business、エッセイ essay）を使います。

### 完了報告

書き直した本文のあとには、「変えたところ」（5点まで）、「残したAIっぽいところ」、「書き手に確かめたい点」（2点まで）、「確認の記録」が付きます。確認の記録は、実行した検査と、実行しなかった検査とその理由を分けて書き、最後に `yomiyasu_check.py` の状態の行（`yomiyasu-check:` で始まる行）を写したものです。Python を実行できない環境では、スキルは検査の代わりに原文と最終稿を読み比べ、状態の行を `yomiyasu-check: not_run reason=no_python` のように書きます。本文だけを返すよう頼んだときは、確認の記録も説明の欄も付けません（検査は同じように行います）。

### 書く前に読ませる使い方

推敲だけでなく、AIに文章を書かせる前にyomiyasuを読ませる使い方もあります。[ai-garageの検証記事](https://ai-garage.jp/column/yomiyasu-claude-writing/)（2026年10月11日、v1.1.1で検証）では、Claude Opus 5.5に8種類のメモから文章を書かせ、書かせ方を4通り比べています。先にyomiyasuを読ませた文章は、メモにない内容を書き足したと指摘された回数が2回で、何も付けずに書かせた場合の60回から大きく減りました。

一方で、文章は平均356字と、依頼した500字程度より短くなりました。読みやすさの評価は4通りの中で最も低く、時間と費用も約4倍かかっています。採点はAIによるもので、文章の種類ごとの本数も少ない、1つの試験の結果です。記事では、この使い方は数字や日付、条件を正確に伝えたい文章（営業メール、障害報告書、手順書など）に向くとしています。エッセイや告知のような読み物には、何も付けずに書かせるか、依頼に一言添えるほうが向くという結論です。エッセイでは、先にyomiyasuを読ませた文章が8回の採点すべてで最下位でした。

2.0.0-beta のスキルに資料から新しく書かせると、スキルは `yomiyasu_check.py run` に資料を `--material` で渡し、最終稿の数値、名前、語、確度の語を資料と照らします。資料にない数値や名前は候補に出ます（新規作成のモード）。


## 付属ツール

文章の表現と書式を見る `yomiyasu_lint.py`、推敲の前後を比べる `yomiyasu_diff.py`、2つをまとめて実行して記録を残す `yomiyasu_check.py` の3つのスクリプトと、共有モジュール `markdown_visibility.py`、設定に貼ったときだけ動く任意のフック `yomiyasu_hook.py` を同梱しています。外部ライブラリは要らず、Python の標準ライブラリだけで動きます。Python 3.8 以上の文法で書いており、自動の試験は macOS の Python 3.9.6 と 3.14.5 で動かしています（3.8 と Windows の実機では確かめていません）。`python3` がない環境では `python` か `py -3` で実行してください。

3つのスクリプトが出すのは、見直し候補と変わった箇所です。意味が保たれたかと、読み手にとって分かりやすいかは判定しません。候補が0件でも、意味が同じだという証明にはなりません。本ツールは特定の構文を対象とする簡易な検査であり、完全なMarkdownレンダラーでもありません。候補をなくすことを目的に機械的に直すのではなく、元の文や文脈と照らし合わせて判断してください。

### 1. yomiyasu_lint.py（表現と書式の検査）

1つの文章について、AIの文章に多い表現（不自然な比喩動詞、決まり文句、過剰な太字・箇条書き、絵文字、文末コロン、同一文末の連続など）と、日本語の括弧や句読点に隣接して表示先の規則により太字として表示されない可能性がある書き方（`bold_not_rendered`）を検査します。複数行にまたがる太字やブロック境界（引用、見出し、リスト、表）も考慮して判定します。

2.0.0-beta からは、通常の出力に点数を出しません。出力の1〜3行目は次の3行で、そのあとに見直し候補を行の順に、規則の ID を付けて並べます。

```text
表現・書式の検査を実行しました。
見直し候補: 3件
この検査では、意味の保持と読者にとっての分かりやすさは判定していません。

内訳: error 0件、warn 3件、info 0件

L3 [WARN] metaphor_verb: 比喩動詞「壊れる」が検出されました。…
```

点数は JSON の `rule_penalty_score` にだけ残しています。規則に当たった件数から引き算した目安で、文章の品質や読みやすさの点数ではありません。合否には使わないでください。

```bash
# Markdownファイルを検査
python3 scripts/yomiyasu_lint.py article.md

# warn か error の候補があれば終了コード1を返す（CIやGitフック用。--strict と同じ）
python3 scripts/yomiyasu_lint.py article.md --fail-on warn

# 文書の種類と読者を指定
python3 scripts/yomiyasu_lint.py slides.md --doc-type slides --reader general

# JSON形式（形式2）で結果を出力
python3 scripts/yomiyasu_lint.py article.md --json
```

- `--strict` か `--fail-on` を付けなければ、候補があっても終了コードは0です。CI で使うときは、点数のしきい値で止めず、候補の中身で止めてください（`--fail-on warn`、太字が表示されない書き方だけなら `--fail-on error`）。止めずに警告として表示するだけの使い方も勧めます。
- 終了コードは、0が検査を最後まで実行して条件に当たらなかったとき、1が `--strict` か `--fail-on` に当たったとき、2が使い方か入力の誤り、3が内部の誤りか、出力先が閉じられて結果を最後まで書けなかったときです。
- `--doc-type` を付けると、その種類で普通な書き方を拾う規則の候補を外し、外した件数を出します（外した候補の中身は、付けずに実行すると見られます）。`--reader` は表示と JSON に残すだけで、候補は変えません。
- 行頭から書いた `<details>` と `</details>` の組の中にある箇条書きは、箇条書きの比率（`excess_list`）に数えません。根拠を `<details>` に畳んだ文書で、過剰な箇条書きの候補が出ないようにするためです。中の箇条書きの行の数は、JSON の `metrics` の `details_list_lines` に出ます。
- JSON の `score` と `is_clean` は、`rule_penalty_score` と `no_rule_findings` に名前を変えました。形式は `data.get("format_version", 1)` で見分けられます（[CHANGELOG](./CHANGELOG.md) の「互換性のない変更」）。

このリンターは、推敲で見落としやすい表現を拾うための補助です。文章をAIが書いたかどうかを判定する道具ではありません。同梱の評価用コーパス（`tests/corpus/`）には、モデルに人の文章らしく書かせた例文が8本あり（`tests/corpus/human/human_doc_*.md`。フォルダの名前は human ですが、人が書いた文ではありません）、8本とも見直し候補は0件でした。候補が少ないことは、人が書いた証拠にはなりません。コーパスの中で人が書いた文章は、作者の記事1本を見出しで8つに分けた抜粋（`human_oga_*.md`）だけです。量が少ないので、人の文章とAIの文章をどれだけ見分けられるかの数値は載せていません。1.1.2 の README に載せた human の16本の数値の訂正は、[CHANGELOG](./CHANGELOG.md) の「訂正」に書いています。

### 2. yomiyasu_diff.py（推敲の前後の比較）

推敲前と推敲後を比べ、変わった箇所をすべて出します（全文差分）。あわせて、意味が変わる恐れのある変化と、語の増減、文末の種類や立場（勧め／決まり／説明）の変化、太字の表示などの見直し候補を出します。

```bash
# 原文と推敲後の差分を検査（文書の立場を指定。--stance 説明 とも書けます）
python3 scripts/yomiyasu_diff.py 元の文.md 書き直した文.md --stance=説明

# 数値・否定・入れ替え・文の種類の変化があれば終了コード1を返す
python3 scripts/yomiyasu_diff.py 元の文.md 書き直した文.md --fail-on=meaning-risk

# 文末の種類（敬体・常体・立場）の分布のみを確認
python3 scripts/yomiyasu_diff.py --endings 対象文.md
```

出力の例です（「田中が佐藤を承認した。設定は3日ごとに保存します。」を「佐藤が田中を承認した。設定は30日ごとに保存しません。」にした場合）。

```text
差分の検査を実行しました。
状態: 変更あり（2か所）。見直し候補 3件、うち意味が変わる恐れ 3件
全文差分は変わった箇所を示すだけで、意味が同じだという証明ではありません。この検査では、意味の保持と読者にとっての分かりやすさは判定していません。

■ 意味が変わる恐れ（3件。原文と資料に照らして確かめる）
- 「が」「を」などが入れ替わった（1行目）: 田中 が→を、佐藤 を→が
  元: 田中が佐藤を承認した。
  後: 佐藤が田中を承認した。
- 数値が変わった（3行目）: 3日 → 30日
  元: 設定は3日ごとに保存します。
  後: 設定は30日ごとに保存しません。
- 否定の有無が変わった（3行目）: 保存します → 保存しません
  元: 設定は3日ごとに保存します。
  後: 設定は30日ごとに保存しません。

■ 全文差分（変更 2か所。省略していません）
@ 元1行目 → 後1行目（本文）
  元: 田中が佐藤を承認した。
  後: 佐藤が田中を承認した。
@ 元3行目 → 後3行目（本文）
  元: 設定は3日ごとに保存します。
  後: 設定は30日ごとに保存しません。
  差: 設定は3{+0+}日ごとに保存しま[-す-]{+せん+}。

状態: 変更あり（2か所）。見直し候補 3件、うち意味が変わる恐れ 3件
```

- 状態は「変更なし」「変更はあるが、専用の規則に当たる見直し候補はない」「変更あり」の3つです。全文差分の `[-…-]` は消えた文字、`{+…+}` は足した文字です。
- 意味が変わる恐れとして出すのは、数値、否定、主語と目的語の入れ替え（「が」「を」など）、問いと平叙、文の種類の印（伝聞、推量、意見、例え、依頼や決まり）、コード・URL・引用など変えない箇所の変化、引用の印（`[1]`、`(山田 2020)` の形）の変化、否定対比の主張の逆転（「Aではなく」で否定していた A が、推敲後に目的や優先の側に出た）、元にない気持ちの語です。
- `--fail-on=meaning-risk` で終了コード1になるのは、このうち数値、否定、主語と目的語の入れ替え、文の種類（問いと平叙、文の種類の印）、引用の印の変化だけです。コード・URL・引用などの変化、否定対比の主張の逆転、元にない気持ちの語は、意味が変わる恐れとして出しますが数えません。付けなければ、候補があっても終了コードは0です。付けたときは、種類を付けなくても、引用の印、統計の値の比較の記号、同じ値の符号が変わった文書で、終了コードが0から1に変わることがあります。
- 推敲で文体が硬くなった箇所（漢字の割合、文の長さ、名詞化の言い回し、漢語の「の」の連続が増えた）と、勢いが落ちた箇所（「！」「？」、絵文字、強める語が減った、見出しが短くなった）は、「■ 文体の硬化」「■ 勢い」の節に見直し候補として出します。この2つは件数と `--fail-on` に入れません。文書の種類によっては参考としてだけ出します（硬化は incident、formal、paper、勢いは pr、article、incident、manual、formal、paper）。検査に使う語の一覧は `references/lists/` にあり、足し引きできます。
- 慎重な言い方（と考えられる、可能性がある、示唆する など）が減った文は「■ 慎重な言い方」に、宛名（〇〇様、〇〇さん）とリンクでないメールアドレスの変化は「■ 動かしてはいけない値」に出します。`--doc-type mail` のときは、敬語の数と「です・ます」の割合が大きく動いた文書を「■ 敬語の度合い」に出します。この3つは見直し候補で、件数と `--fail-on` に入れません。同じ文で推量の印が消えたときは、文の種類の印の候補に任せて、慎重な言い方には重ねて出しません。
- 推敲の前後で文を1文ずつ対応させて、文の種類の印が消えたり増えたりした文も示します。文の対応は字面の重なりでたどるため、大きく言い換えた文や順番を大きく入れ替えた文では、変化を取りこぼしたり、対応しない文どうしを比べた候補が出たりすることがあります。候補に出なかった文も、元の文と読み比べてください。
- 終了コードは、0が比べ終わって `--fail-on` に当たらなかったとき、1が `--fail-on=meaning-risk` に当たったとき、2が使い方か入力の誤り、3が内部の誤りです。

### 3. yomiyasu_check.py（検査をまとめて実行し、記録を残す）

最終稿に lint を、原文と最終稿に diff をまとめて実行し、記録を残します。スキルは、書き直しのあとに `run` を、提出の直前に `verify` を実行します。

```bash
# 推敲: 原文と最終稿を渡す（資料があれば --material 資料 を足す）
python3 scripts/yomiyasu_check.py run --source 原文.md --final 最終稿.md --doc-type article

# 新規作成: 資料と最終稿を渡す（資料との照合と lint）
python3 scripts/yomiyasu_check.py run --material メモ.md --final 最終稿.md

# 提出の直前に、最終稿が検査したものと同じかを記録と照らす
python3 scripts/yomiyasu_check.py verify --final 最終稿.md
```

出力の2行目は、次のような状態の行です。完了報告の確認の記録には、この行を写します。

```text
yomiyasu-check: executed via=verify run=20261014T124830Z-6b5d53f8 attempt=1 final=sha256:6aa6ecba24a9 mode=rewrite doc_type=article checks=lint,diff meaning_risk=0 replay=ok
```

- 返す状態は「検査を実行した」（`executed`）で、合格ではありません。run は、検査の一部を実行できなければ `partial`、使い方の誤りなら `not_run` を返します。verify は、記録がない（`no_record`）、検査のあとに最終稿を書き換えた（`final_changed`）、記録のあとに検査スクリプトや語の一覧が変わった（`tool_changed`）ときなどに、完了と扱いません。diff を実行していない記録と、別の原稿の記録も、完了と扱いません。書き直す前の文章を資料として渡しても、資料が最終稿とよく似ていれば、run はそれを原文とみなして diff も実行します。
- 記録は、git の最上位（なければ作業ディレクトリ）の `.yomiyasu/` に置きます。自分を無視する `.gitignore` を作るので、git には出ません。先にできていた `.yomiyasu/` でも、`.gitignore` と `state.json` がどちらもなければ作ります。場所は `--state-dir` か環境変数 `YOMIYASU_STATE_DIR` で変えられます。こうして指定したフォルダがすでにあるときは `.gitignore` を足さないので、git に入れたくなければ利用者が無視の設定をしてください。記録には原稿の写しが入りますが、外へは送りません。要らなくなれば消してかまいません。
- 記録は実行漏れを見つけるためのもので、改ざんの防止や人の承認の証明にはなりません。同じ権限で原稿と記録の両方を書き換えられる環境では、記録を作り込むこともできます。`verify --replay` は記録の写しで lint と diff を動かし直し、結果が記録と同じかを確かめますが、写しと結果を同じように作り込んだ記録は見分けられません。
- ファイルを作らない対話では、`run --stdin` で原文と最終稿を標準入力から渡します。行全体が `<<<yomiyasu:original>>>`、`<<<yomiyasu:material>>>`、`<<<yomiyasu:final>>>` の行で区切ります。この使い方にはシェルが要ります。ファイルを作らない対話では、スキルは提出前の verify を行わず、完了報告の「実行しなかった検査」に最終稿の照合を書きます。
- `--fail-on meaning-risk` は diff と同じ種類に、資料から書いたときの資料にない数値を加えて数えます。`--fail-on warn` と `--fail-on error` は lint の候補で止めます。どれも、記録を残したうえで終了コード1を返します。
- 終了コードは、0が run で条件に当たらなかったとき・verify で記録と合ったとき、1が run で `--fail-on` に当たったとき・verify で記録がないか合わないとき、2が使い方か入力の誤り（何も書きません）、3が検査の一部を実行できなかったときか内部の誤りです。

### 4. yomiyasu_hook.py（任意のフック）

フックは、ホストが決まった時点で動かすコマンドです。yomiyasu_hook.py は、登録した原稿について、検査を実行したか、最終稿が検査記録と同じかを、返答の終わりと投稿の前に確かめます。入れなくても yomiyasu はこれまでどおり使えます。利用者が自分の設定ファイルに貼ったときだけ動き、スキルやプラグインを入れただけでは動きません。

フックは、読みやすさの合格や、意味が保たれたかを判定しません。会話の中の日本語を書き換えたり、登録していない原稿の保存や投稿を止めたりもしません。

#### 登録のしかた

対象になるのは、登録した原稿だけです。

- 端末で `python3 -B /path/to/yomiyasu/scripts/yomiyasu_check.py start --source docs/draft.md` を実行します。最終稿を別のファイルに書くときは `--final docs/final.md` を足します。
- Claude Code では、プロジェクトに置いたスキルを `/yomiyasu docs/draft.md を読みやすくして` のように呼び、原稿のファイルを書くと、フックが登録します。登録するのは、依頼の文で最初に出てくるファイル1つだけです。2つ以上の原稿は、端末で1つずつ `start` してください。
- Codex では、`$yomiyasu:yomiyasu docs/draft.md を読みやすくして` のように依頼の文にスキルの名前を書くと、フックが登録します。`$yomiyasu` と書いても登録します。登録するのは、Claude Code と同じく最初に出てくるファイル1つだけです。試した置き方では Codex がスキルを `yomiyasu:yomiyasu` という名前で一覧に載せたので、`$yomiyasu` と書いた回ではスキルの指示が読み込まれませんでした。

#### 入れ方

1. `python3 /path/to/yomiyasu/scripts/yomiyasu_hook.py --print-config claude-code` で、このスクリプトの絶対パスを入れた設定の例を出します。設定ファイルには書き込みません。
2. 出た JSON を、管理したいプロジェクトの `.claude/settings.json` か `.claude/settings.local.json` に貼ります。`~/.claude/settings.json` に貼るとすべてのプロジェクトで動き、Bash と MCP のツールを呼ぶたびに python が起動します。
3. プラグインを更新するとスクリプトのパスが変わります。更新したら、設定の例を出し直して貼り直してください。

Codex では次のように入れます。

1. `python3 /path/to/yomiyasu/scripts/yomiyasu_hook.py --print-config codex` で設定の例を出します。
2. 出た JSON を、管理したいプロジェクトの `.codex/hooks.json` に置きます。
3. Codex は、信頼していない hooks.json を、何も知らせずに飛ばします。試したのは、`codex exec` に `--dangerously-bypass-hook-trust` を付けて信頼の確かめを飛ばした形だけです。`/hooks` で信頼する手順は試していません。
4. `codex exec` に `--ignore-user-config` を付けると、プロジェクトの `.codex/hooks.json` も読まれず、フックは1つも動きません（1回確かめました）。

#### 動き

- 返答を終えるたびに、登録した原稿の最終稿が検査記録と合うかを確かめます。合わなければ、理由を渡して作業を続けさせます。続けさせるのは2回まで、登録から30分まで、run は3回までです。超えたら「未確認」として1回知らせ、それ以上は続けさせません。自動で書き直したり投稿したりはしません。上限は `start` の `--max-stop-blocks`、`--max-runs`、`--deadline-min` で変えられます。
- Claude Code は、フックが作業を続けさせたときに「Stop hook error occurred」と表示し、投稿を止めたときに「PreToolUse:Bash hook error:」に続けて理由を表示します。どちらも、フックの判断を知らせる表示です。
- Codex の `codex exec` では、続けさせる理由が利用者の入力としてエージェントに届きます。投稿を止めたときは「Command blocked by PreToolUse hook:」に続けて理由が出ます。
- 投稿には、`yomiyasu_check.py export --final 最終稿` で書き出した写しを使ってください（例 `gh pr create --body-file <写し>`）。写しは `.yomiyasu/exports/` にでき、検査した最終稿と同じバイト列です。照合が合わないときは写しを作りません。写しができても、合格の判定ではありません。
- 補助として、登録した原稿に関係する `gh` の投稿（pr、issue、release の本文と、api の本文の欄）と MCP の投稿で、本文が検査記録と照合できないときは止めます。`--body "$(cat 最終稿)"` のように本文を取り出せない投稿は、利用者に確かめます（Claude Code の `-p` では実行されません）。Codex には利用者に確かめる仕組みがないので、止めます。登録と関係ない投稿は止めません。
- `yomiyasu_check.py end --source docs/draft.md` で登録を終えられます。セッションが終わったときも終わります。Claude Code の `-p` では1回ごとにセッションが終わるので、端末で登録した原稿が効くのは `-p` の1回分です。`--resume` で続けても、前の回の登録は引き継がれません。
- 登録のある原稿の run は、上限を超えると検査せずに `unverified` と終了コード1を返します。登録の無い原稿の run と verify は、フックを入れる前と同じです。

#### フックの限界

- フックは補助で、確かめていない原稿の公開を完全には止められません。フックの時間切れや失敗、一覧にないコマンド（`gh` 以外）、本文を取り出せずパスも書いていない投稿、本文を少し変えた投稿、利用者が自分で行う投稿は止まりません。
- 返答の中だけで推敲し、ファイルに書かなかったときは、フックでは見つけられません。
- Codex の `codex exec` では、「未確認」の知らせが利用者に表示されません（JSON の出力で2回、人向けの出力で1回確かめました）。フックは知らせを出していますが、Codex が表示しません。上限で止まったときは、エージェントの完了報告の「実行しなかった検査」を見て、投稿の前に `yomiyasu_check.py verify` で確かめてください。
- 試した Codex では、エージェントのコマンドはコード実行のツール（`exec_command`）を通り、`Bash` としてフックに届きました。ほかの経路でコマンドを実行したときにフックが見るかは、確かめていません。
- 同じプロジェクトで2つのセッションを同時に動かすと、端末で登録した原稿は、先に動いたセッションのものになります。取り違えを避けたいときは、`start --session` でセッションを指定します。
- 登録、記録、写しは `.yomiyasu/` にあり、エージェントと同じ権限で書き換えられます。改ざんの防止や人の承認の証明にはなりません。フックはネットワークを使わず、本文を外へ送りません。フックの出力と登録のファイルにも、本文は入れません。

## 限界

付属の検査（lint と diff、2つをまとめて実行する check）は、決まった形を拾うものです。意味が保たれたかと読みやすいかは、元の文と読み比べて人が確かめてください。候補が出なくても、変わった箇所は全文差分に出ます。以下は 2.0.0-beta の時点で分かっている限界で、細かい形は各項目の「細かい形」を開くと読めます。

### 確かめた範囲

2.0.0-beta のスキルを実際に動かして確かめたホストは Claude Code だけです。Codex、Cursor、Claude.ai のZIP、skills CLI や openskills で入れた環境では確かめていません。Windows の実機でも確かめていません。

手順を飛ばす割合（検査のあとに本文を直して、直した本文に検査をかけない、など）が 1.1.2 より下がったかは、まだ測っていません。記録で見つけやすくなりましたが、記録があっても手順を飛ばすこと自体は防げません。

意味が変わった箇所を diff がどれだけ拾うかは、少ない数でしか測っていません。tests/corpus の推敲の48組（古いバージョンの yomiyasu の指示で作った推敲の出力）を3つのモデル（Gemini 4 Argon、Gemini 3.8 Flash、Claude。3.8 Flash が判定したのは48組のうち44組）に判定させると、2つ以上のモデルが意味が変わったとした箇所は31か所ありました。そのうち、意味が変わる恐れの候補と重なったのは0か所で、全文差分には28か所が出ます。31か所のうち19か所は、原文にない担当者を主語や通知先に足したもので、今の検査の種類にありません。モデルの判定は参考で、確かめは人が行います。

AI が書いた原稿8本と合成の原稿2本（合計4,546字）を、スキルなし、1.1.2、2.0.0-beta の3条件で Claude Code に1回ずつ推敲させた小さな比べでは、2つのモデル（Claude と Gemini 4 Argon）がそろって意味が変わったとした箇所は、3条件とも0件でした。2.0.0-beta と 1.1.2 の差は偶然の幅に収まり、モデルの判定からは、どちらが意味を保ちやすいとは言えません。

同じ比べで 1.1.2 と 2.0.0-beta の本文が違った7組を、作者が版名を隠して読み比べると、好みは 1.1.2 が6組、2.0.0-beta が0組、同等が1組でした。そのまま使えるとした出力は、1.1.2 が6組、2.0.0-beta が0組です（2.0.0-beta は、少し直せば使えるが4組、使えないが3組）。1人が各条件1回の出力を見た小さな比べですが、この比べでは、2.0.0-beta の推敲は 1.1.2 より好まれませんでした。上の2つの比べの 2.0.0-beta は、SKILL.md を組み直す前のものです。組み直したあとの今の SKILL.md の推敲は、まだ人が 1.1.2 と読み比べていません（組み直しの経緯は CHANGELOG の「変更」）。

### 数値

表記だけの違い（漢数字と算用数字、範囲・日付・時刻の書き方など）は候補にしないよう作っていますが、万と億を含む数の換算（一万円 → 1万円）、「.」で区切った日付、時刻の「:00」、「0円 → 無料」などは、値が同じでも候補に出て、`--fail-on=meaning-risk` に数えます。逆に、範囲の端の値を別の値として書き直した形、平仮名の数（ひとつ、ふたり）を足しただけ・消しただけの書き換え、助数詞の一覧にない語（冊、点、票）の数の変化などは拾えません。

<details>
<summary>細かい形（正しい推敲にも出る形）</summary>

万と億を含む数の換算（一万円 → 1万円）、「.」で区切った日付（2026.10.13 → 2026年10月13日）、時刻の「:00」（9:00 → 9時）、「v2.0 → バージョン2.0」「0円 → 無料」、「一度」と漢数字の並び（一度 → 1度、第三四半期 → 第3四半期、三四人 → 3〜4人）、前に何もない「一時」（一時三十分 → 1時30分。一時的の「一時」と分けられない）、「じゅうぶん」と分けられない「十分」（一回十分です → 1回10分です、八時間十分働いた → 8時間10分働いた）は、値が同じでも候補になります。直前が漢字の漢数字（夜一人で）は数として取らないので、助詞を足しただけ（夜に一人で）でも候補になります。回数を言わなくした書き換え（月一回 → 毎月）、「一人十分の量 → 一人あたり十分な量」、「層を1枚挟む → 層を作って前に置く」は、消えた数値として出ます。数を言わない語を数字で言い直した推敲（一意 → 1つ、倍々 → 2倍ずつ、単体 → 1件ずつ、集約 → 1件にまとめ）と、助数詞だけを替えた推敲（3〜4本 → 3〜4回）も候補になり、--fail-on に数えます。序数の「1つ目 → 最初の」は消えた数値、「一つずつ → 一枚ずつ」は元にない数値になります。同じ単位の数の前後を入れ替えただけの推敲（ひとりで3人分を食べた → 3人分をひとりで食べた）は、並びの候補になります。「ずつ」のあとに動詞がない文は、相手の文のどこかに「複数」「いくつか」があれば、順番に、と言い換えた正しい推敲（質問は一つずつどうぞ → 質問は順番にどうぞ。複数ある方も順番にお願いします）でも消えた数値になります。「一つずつ」の動詞や「一つの」の名詞を言い換えた1つの文では、主題と同じ語を主語にした節（似た質問が複数届いたら一覧にします）、主語のない節（版ごとに別々の名前を付けます）、送り仮名の途中で切れる主語の節（問い合わせが複数重なれば）にある 複数・いくつ・別々 を数えるので、別の物の数を言い換えただけの推敲でも消えた数値になります。数の主張が同じ語（順に）があっても、前から数えていた語（まとめて）が別の述語に付けば、消えた数値になります（ファイルは一つずつ確認する → ファイルを順に見て、結果はまとめて送る）。
</details>

<details>
<summary>細かい形（拾えない形）</summary>

範囲の端の値を、同じ文の別の値として書き直した形（3〜5日かかる → 5日で終え、予備に3日をとる）、数量を言っていない漢数字の「一つ」や期間の値を言わなくなった書き換え（今日一日で終える → 今日から数日で終える）、2つの文をまとめたときに組にならなかった文の「一つずつ」の変化、読点を挟まずに別の述語の打ち消しが続く形（一つずつ行う → 並列で行い遅延を出さない）、前に何もない「一時十分に → 一時に」、助数詞の一覧にない語（一人一票 → 一人二票。冊、点も同じ）と「お一人様一つ」の数の変化は、候補に出ません。数量を言っていない「一つ」と同じ扱いなので、「もう1つ」「1つの」を足した・消した書き換えは、数を限る意味でも拾いません（理由がある → もう1つ理由がある、同時に使える端末は1つの端末だけです → 同時に使える端末に制限はありません。「1つの」を含む文を消した推敲も同じです。資料から書いた最終稿の「1つの画面にまとめました」も、資料にない数値にしません）。平仮名の数は相手の文に同じ単位の値がないと比べないので、足しただけ・消しただけの書き換え（会議室はふたつある → 会議室がある）と、「ふたつしか」「ひとりだけ」「ふたりまで」「ふたつずつ」を言い換えた書き換えは拾いません（漢数字なら拾います）。資料から書いたときの照合でも、平仮名の数は資料の値と違っても候補にしません（参考の行に資料の値が出ます）。「に」「で」のすぐあとの「いつつ」は数として取らないので、「箱にいつつ入れる」の数の書き換えも拾いません。文を分けて「複数」「いくつでも」を別の文に置いた推敲（ファイルは一つずつ送ってください → ファイルを送ってください。複数あってもかまいません）と、「一つの」の名詞のある節から離して「別々」を置いた推敲（鍵は一つの金庫にしまう → 鍵は別々の場所にある金庫にしまう）は拾いません。数値の直前の2字とあとの語が同じ入れ替え（上限は10GB、下限は500MB → 上限は500MB、下限は10GB）、直前が読点の数の入れ替え（設計に3日、5時間を試験に充てる → 設計に5時間、3日を試験に充てる）、同じ助詞のあとの「約」の数の入れ替え（設計に約3日、試験に約5時間 → 設計に約5時間、試験に約3日）は、並びの候補にしません。
</details>

### 否定

語ごと言い換えた否定（確認します → 確かめません）は、否定の候補に出ません。文を分け、否定を別の言い方で次の文に移した推敲（…形に変えてから、抜けた通知の調査は発生していません → …ています。この形に変えてから、抜けた通知を調べる事態は起きていません）は、正しい推敲でも否定の候補になり、--fail-on に数えます。

### 否定対比の主張の逆転

平仮名で始まる語（お知らせ）と漢字1字の語は、否定された語として取りません。見出しや「Aは使わず」の文、一覧にない言い方で A を後ろへ回した推敲などでは、正しい推敲にも候補が出たり、逆転を見逃したりします。否定した側を消しただけの推敲は候補にしません。逆転は `--fail-on` に数えないので、候補が出たら、A が目的や優先の側に移ったかを読んで決めてください。

<details>
<summary>細かい形</summary>

「お知らせ」のように平仮名で始まる語と、漢字1字の語（人ではなく仕組み）は、否定された語として取りません。「Aも含めて」の形も拾いません。見出しの行と「Aは使わず」「Aはせず」の文では、A を足しただけの書き換え（外部委託はせず、社内で作ることを最優先にします → 社内で作ることを最優先にし、外部委託も使います）と、別の節の語が A を指す書き換え（表計算は使わず → 表計算で入力し、これを最優先の手順にします）を拾いません。一方、一覧にない言い方で A を後ろへ回した推敲（来期に回す、Aに手を付けるのは見送る、Aは優先順位を下げる）は、正しい推敲でも候補に出ることがあります。下げる語は A のすぐあとに続く形だけを見て、「そのあとに回す」は平仮名の書き方だけを見るので、読点を挟んだ形（Aは、その次に見る）や「その後に回す」「次に見る」も、正しい推敲で候補に出ます。別の名詞のあとの「は後に回す」（品質を最優先にして速度は後に回す）の逆転は拾いません。主題の句（最優先は、大事なのは など）のあとに、置き換え先を言わずに A を変える言い方を置いた正しい推敲（## 大事なのは、会議を最小限にして文書で決めること）は、原文で肯定した側の語を使っていても逆転の候補に出ます。重みの語だけの句（まず、第一に など）のあとでも、原文で肯定した側の語を使わずに A を変える・取り除く・調べる言い方（減らす、絞る、洗い出す、時間を測る、A を別のものにする・別のものに変える。## まず、手作業を洗い出す）は、正しい推敲でも候補に出ます。読点を挟んで置き換える言い方（Aを、B に置き換える）も同じです。本文の「Aではなく」の推敲は、重みの語が文のどこにあっても見るので、原文で肯定した側の語を使った正しい推敲（まず、手作業を自動化する）でも候補に出ます。一方、重みの語だけの句のあとで A と B の語を両方使った逆転（## 会議ではなく文書で決める → ## まず、会議で決めて文書で知らせる）は拾いません。B を廃止する・見送る・控える・禁止する・なくす・頼らない、と言う逆転と、B より A を優先する・B を後回しにする、と比べて下げる逆転（## まず、会議を文書より優先する）も拾いません。逆に、置き換え先や A を使う句が一覧にない言い方（試作版を正式版に移行する、クラウドを主にした構成に切り替える）は A を下げた形とみなすので、A を採った推敲を見逃すことがあります。逆転は --fail-on には数えません。

否定した側を消しただけの推敲（AではなくB → B、Aに任せず → 消す）と、「Aにすぎず」の言い換えは、候補にしません（逆転だけを見る検査です）。
</details>

### 文の種類の印、気持ちの語

依頼を前置きする文を依頼の文にした推敲（お願いしたいことは3点あります → 次の3点をお願いします）と、結果を言う文を義務の文にした推敲（修正につながります → 修正しなければなりません）は、文の種類の候補になり、--fail-on に数えます。

元にない気持ちの語の検査（一覧は `references/lists/feelings.txt`）は、一覧の語だけを見ます。同じ語が原文のどこかにあれば、別の所に足しても出ません。「売上が前年より落ち込んだ」のように間に語が入る形と、「苦しい言い訳」のような気持ちでない使い方は、候補に出ます。

### 文体の硬化と勢い

変わった文が1つだけの文書では、1文の条件に当たらない小さな硬化は出ません。勢いは、評価の語を短く重ねる型を1文にした推敲と、一覧にない褒め言葉の繰り返しを減らした推敲を拾いません。種類を指定しないと、定型の結びを消した推敲のような正しい直しも、勢いの見直し候補になります。

<details>
<summary>細かい形</summary>

promo でも、箇条書きの太字の行（- **…**）は見出しに数えません。ほかの種類では、番号つき項目の行と太字だけの行も数えません。評価の語を短く重ねる型（安い。うまい。早い。）を1文にした推敲と、強める語の一覧にない褒め言葉（絶品など）の繰り返しをまとめて減らした推敲は拾いません（紹介記事ではどちらも残す決まりなので、読み比べて確かめます）。種類を付けないときは、AIの定型の結び（「いかがでしたか？」「ぜひご活用ください」）を消した推敲や、技術文書の「！」を句点にした推敲のような正しい直しも、見直し候補になります。
</details>

### 慎重な言い方、引用の印、宛名、敬語の度合い

慎重な言い方は、一覧（`references/lists/hedges.txt`）の7つの語と同じ文字の並びだけを見るので、「示唆した」「示唆される」のように形の変わった語が減っても拾いません。引用の印は、数字の角括弧と、著者と年をまとめた括弧の形だけで、本文に著者を書いた形（山田 (2020) によると）の著者の変化と、引用の印を別の文へ動かした推敲は拾いません。英字の著者は年の前に「,」か「et al.」があるものだけを見ます（(Smith 2019) は拾いません。(Windows 2000) のような製品名と年の括弧を引用と取らないためです）。漢字の名前と年の括弧（(東京 1998) など）は引用として見ます。符号は、直前が漢字や片仮名のときは見ません（「10月-12月」の範囲を負の数と取らないためで、「前年比-5%」の符号も見ません）。宛名は行の頭と宛先の欄のものだけを見ます。敬語の度合いは文書全体の割合で比べるので、短いメールでは1文の違いでも候補になり、長い文書では1文の変化を拾いません。「ください」も「くださる」に数えるので、「〜いただけますでしょうか」を「〜してください」にしても候補は出ません。文末の割合は「です・ます」と「だ・である」の文だけで数えるので、チャットの口語（〜かも、〜しときます）を「です・ます」にそろえても候補は出ません。二重敬語を正しく直すと（ご確認させていただきました → 確認いたしました）、敬語の数が減って候補が出ます。mail と paper の推敲の指針（`references/doc-types/mail.md`、`paper.md`）は、モデルに推敲させて結果を測っていません。tests/corpus には実際のメールと論文がほとんどなく、正しい推敲の48組で3つの検査の候補が0件だったことから、拾い漏れが少ないとは言えません。

### lint の `<details>` と check

lint が箇条書きの比率から外すのは、行頭から書いた `<details>` と `</details>` の組の中だけです。

<details>
<summary>細かい形</summary>

行頭から書いた開きと閉じが組になったときだけ見ます。段落の途中に書いた `<details>`、閉じていない `<details>`、引用の中の `<details>`、`:::details` のような Markdown の拡張の書き方は見ず、中の箇条書きを今までどおり数えます。`<details open>` も畳んだものと同じに扱います。ライブラリとして `lint_text()` を呼ぶときは、先頭の BOM を外した文字列を渡してください（BOM が残ると1行目の `<details>` を見ません。コマンドは BOM を外して読みます）。
</details>

本文に `<<<yomiyasu:` で始まる行がある文書は、`--stdin` では渡せません（ファイルで渡します）。6万字ほどの文書の全体を書き換えると、run の既定の `--timeout`（90秒）では diff が終わらず、結果が partial になります（全面書き換えの合成の文書で測ると、`--timeout 1500` にして約15分で executed になりました）。小さな修正なら、6万字でも10秒ほどで executed になります。

- Zaitsu et al., [Stylometry can reveal artificial intelligence authorship, but humans struggle](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0335369), PLOS One 2025

- 三浦・久保山, [生成AIは文体を均質化するのか？](https://www.jstage.jst.go.jp/article/pjsai/JSAI2026/0/JSAI2026_5YinA18/_article/-char/ja/), 人工知能学会 2026 / 林・相澤, [LLMによる日本語生成におけるモデル固有表現パターンの分析](https://www.anlp.jp/proceedings/annual_meeting/2026/pdf_dir/B9-17.pdf), 言語処理学会 2026

- 李・長谷部, [ChatGPTによる日本語ニュースの平易化 生成AIと『やさしい日本語』](https://www.jstage.jst.go.jp/article/mathling/34/8/34_563/_article/-char/ja), 計量国語学 34巻8号

  強調やリストへの評価偏向、英語直訳思考の影響を理解するための補助資料として活用しました。
