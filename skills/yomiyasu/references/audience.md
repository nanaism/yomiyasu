# 文書の種類と読者

SKILL.md 1章の種類と読者の決め方の細部。種類か読者の推定に迷うとき、informed か general を指定されたとき、読者像（ペルソナ）を受け取ったとき、「ここに説明が必要です」を書くときに読む。どの種類と読者でも、意味を保つこと（SKILL.md 4.1）、足さないこと（4.2）、見出しと節の数と順を変えないことは同じ。

## 1. 種類の手がかり

| 種類 | 依頼の手がかり | 本文の手がかり |
|---|---|---|
| pr | PR、プルリクエスト、変更の説明 | 概要、変更点、テスト、確認したことの見出し。Issue の番号、ファイル名、ブランチ名 |
| article | 技術ブログ、Zenn、Qiita、記事 | 導入の段落、コードの囲みとその説明、「本記事では」 |
| incident | 障害、インシデント、ふりかえり | 発生日時、影響範囲、原因、暫定対応、再発防止。時刻つきの経過 |
| proposal | 提案、企画、稟議 | 背景、目的、提案、費用、期待する効果。判断を求める文 |
| minutes | 議事録、会議のメモ | 日時、出席者、議題、決定事項、宿題の欄 |
| manual | 手順書、マニュアル、使い方 | 番号つきの手順、「〜してください」の連続、前提条件、注意 |
| slides | スライド、発表資料、登壇 | `---` のページの区切り、Marp などの先頭の設定、ページごとの短い見出しと箇条書き |
| essay | note、エッセイ、日記、小説 | 一人称の語り、体験と気持ち、会話文と地の文 |
| formal | 規程、契約書、公用文、仕様書、約款 | 第1条などの条の番号、「〜するものとする」、甲と乙、定義の条、施行日や契約の期間 |
| promo | 紹介記事、宣伝文、おすすめ記事、商品やお店の紹介 | 「〇選」「おすすめ」「イチオシ」の見出し、ランキングや一覧の形、価格や購入先の案内 |

- どれにも当たらない文書（全社向けのお知らせ、週次報告、チャットの共有文、リリースノート、メール、DM）は種類を決めない。
- 商品やお店を勧める記事は、note や個人のブログに載せる個人の記事でも promo にする（essay の手がかりにも当たるが、勧める記事なら promo を主な種類とする）。
- 仕様書は formal にする（読み手が決まりとして従う文書）。使い方を手順で示す文書は manual。1つの文書が2つの種類にまたがるとき（台本つきのスライド、提案を含む議事録）は、主な種類が1つに決まればそれにし、決まらなければ決めない。
- 文書の立場（勧め、決まり、説明）は種類とは別に決める。種類から立場を決めない。

## 2. 読者の手がかり

- 依頼の宛先（「全社員向け」は general、「チームの開発者に」「レビュアーに」は expert、「上長に」は informed）と、置き場所（社内 Wiki、公開のブログ、顧客向けのお知らせ）。
- 本文が略語を説明なしで使っていることは弱い手がかりにとどめる。書き手の想定を示すだけで、読む人が専門家とは限らない。
- 種類から決める既定の読者は、pr と minutes の expert（レビューする開発者と、会議の出席者）だけ。

## 3. 推定で進めてよいとき

- 種類: (a) 依頼の行き先か宛先が1つの種類を示し、本文にほかの種類の手がかりがない。(b) 本文に1つの種類の手がかりが2つ以上あり、ほかの種類の手がかりがない。ただし minutes と slides は、本文の形の手がかり（出席者と議題の欄、`---` のページの区切りか Marp の設定）が少なくとも1つ要る。
- 読者: (a) 依頼か宛先が読者を示す。(b) 種類が pr か minutes で、依頼と本文に expert と食い違う手がかりがない。
- どれにも当たらなければ自信がないとする。依頼の行き先（note に載せる、社内 Wiki に置く）から決めたものも、指定ではなく推定とする。
- 指定と本文の形が食い違うとき（「議事録です」と言われたが本文は提案書の形）は指定に従い、本文を種類の形に組み替えない。

## 4. 確かめるか、決めずに進むか

1. 決め方で直し方が変わらないなら、確かめずに決めない。種類なら、候補の種類どうしで外す規則と普通な書き方が同じとき（提案書か技術記事か迷うが、どちらも外す規則がない）。読者なら、説明のない分野の用語、略語、社内の呼び名がないとき。
2. 直し方が変わり、問い返せるなら、書き直す前に1回だけ確かめる。
3. 次の場面では問い返さず、決めずに進む。本文だけを返す指定がある。ほかのスキルの途中で呼ばれた。利用者が「確かめずに」「おまかせで」「質問しないで」と頼んだ。一回きりの実行（`claude -p`、`codex exec`、CI、フック。依頼に返事を待てない旨があるか、ホストから分かるとき。分からなければ問い返せるものとする）。同じ依頼の中ですでに1回確かめた（複数の原稿をまとめて直す依頼でも1回だけ）。

問いは種類と読者を1つにまとめ、番号の選択肢と「おまかせ」を出す。各選択肢に、選ぶと直し方の何が変わるかを短く添える。推定の候補を先に並べるが、どれも勧めない。原稿の評価や直し方の提案を混ぜない。

```text
書き直す前に1つだけ確かめます。番号で答えてください。
文書の種類: 1. スライド（短い箇条書きと見出しをそのまま残します） 2. 技術記事 3. おまかせ
読み手: 1. 同じ分野の専門家（用語を残します） 2. 分野は違うが技術に詳しい人 3. 専門知識のない人（説明が要る所をお返しします） 4. おまかせ
```

- 番号の答えは指定として扱う。
- 「おまかせ」、分からない、答えずに別の依頼を出したときは、その軸を決めず、もう確かめない。
- 選択肢にない説明（「経理の人が読む」）は読者像として受け取り、11章で段階を決める。決まらなければ決めない。

## 5. 決めないとき

- 種類を決めない: SKILL.md 1章の種類の表と doc-types のファイルを使わない。分野が分かれば domains のファイルを読む。check に `--doc-type` を付けない（lint はすべての規則を当てる）。
- 読者を決めない: 用語は SKILL.md 4.4 の「直訳の語と専門用語」の行のとおりに扱う。説明が要る所は返さない。check に `--reader` を付けない。
- どちらも、SKILL.md 4章の基本の規則だけで直す。

## 6. 推定のときに使う調整の範囲

| 調整 | 指定（確かめた答えを含む） | 推定 |
|---|---|---|
| 種類で外す規則と、その種類で普通な書き方を直さないこと | 使う | 使う |
| 用語を残し、説明を足さない（expert） | 使う | 使う |
| 識別子が主語の文を直さない（expert、informed） | 使う | 使う |
| 説明が要る所を返す（informed、general） | 使う | 使う |
| 用語を言い換えるか、原文と資料の説明を添える（informed、general） | 使う（8章の条件のとき） | 使わない。語を残して説明が要る所に出す |
| 文を分ける範囲を広げる（general） | 使う | 使わない |

推定で使う調整は、どれも本文を変えないか、変える箇所を減らす向きにだけ働く。推定が外れても、本文の書き換えは種類と読者を決めないときより増えない。

## 7. 読者の3段階

| 値 | 意味 | 用語の扱い | 文の長さと省略 |
|---|---|---|---|
| expert | 文書の分野の用語と前提を共有している | 用語、略語、識別子を残す。説明を足さず、説明が要る所も返さない | 分野で普通の省略を残す。長い文を分けるのは読み違いを特定できたときだけ |
| informed | 一般の技術や業務の語は分かるが、この分野だけの略語、社内の呼び名、前提の手順は知らない | 一般の技術語と業務語は残す。分野の外で通じにくい語と社内の呼び名は、指定されたときだけ原文と資料の説明で言い換えるか添え、ほかは返す | expert と同じ |
| general | 分野の用語と前提を知らない | 説明のない用語は、指定されたときだけ、原文と資料の説明か同じ範囲を指すふだんの語で言い換えるか添え、ほかは返す | 9章 |

- 技術の文書でないとき、informed は「仕事の文書を読み慣れていて、一般の業務の語は分かる人」と読む。
- 開発者向け（読者が expert か informed で、本文がソフトウェアの話）では、識別子が主語の文（`scheduler` が失敗したジョブを再投入する）を擬人化として直さない。「コードが語る」のような本当の擬人化は直す。general でも識別子は言い換えない。

## 8. 用語の扱い

| 分類 | 例（合成） | expert | informed | general |
|---|---|---|---|---|
| A 原文か資料に説明がある用語 | 「TTL（キャッシュを残す時間）」と原文にある | 残す | 残す | 残す |
| B 説明のない分野の用語と略語 | 冪等、p95、減価償却、発注点 | 残す | 一般の技術語と業務語（API、サーバー、売上原価）は残す。分野だけの語は、資料に定義があり指定されたときだけ言い換えるか添え、ほかは返す | 資料に定義があり指定されたときだけ言い換えるか添え、ほかは返す |
| C 社内の呼び名、内部の略語、プロジェクト名 | 青環境、P1対応、月次締め会 | 残す | 返す（資料に説明があり指定されたときは添える） | 同左 |
| D 直訳の語、AIの造語、意味のぼやけた流行語 | 版、回帰、判断OS、解像度 | SKILL.md 4.4 の行のとおり（slop-catalog.md 2章、5章） | 同左 | 同左 |
| E 識別子、コード、画面の項目名、製品名、法令の用語、数値と単位 | `retry_limit`、「保存」ボタン、PostgreSQL | 残す（識別子が主語の文も残す） | 同左 | 残す。言い換えない。要れば返す |
| F 同じ範囲のふだんの語がある外来語 | アサイン、アジェンダ | 残す | 残す | 指定されたときだけ、同じ範囲のふだんの語に言い換えてよい |

言い換えてよいのは、次のすべてを満たすときだけ。

1. 利用者が informed か general を指定した（確かめた答えを含む）。推定では言い換えない。
2. 言い換えの語が原文か資料の定義から取れる。または、ふだんの語で指す範囲が同じと言える（狭めも広げもしない。分類 F）。モデルが知っている一般の知識で定義を書かない。それは原文にない説明になる。
3. 言い換えが1つに決まる。
4. 「変えたところ」に「用語 → 言い換え（読者: general）」と1行で書く。

言い換えない語は、分類 E のすべて、原文で定義された語、見出しや表の項目名と本文で対応している語、引用の中の語。提供された定義や値と状態の対応を説明に使う決まり（SKILL.md 4.2）は、読者によらず同じに当てる。

## 9. 文の長さと省略

- 種類ごとの長さと省略は、doc-types の各ファイルの3章に従う。
- general を指定されたときだけ、1文に用件が2つ以上あり、つなぎ言葉で関係を残せる文を分けてよい（SKILL.md 4.4 の「読みにくい長い文と読点」の範囲）。推定の general では分ける範囲を広げない。
- 数値の目安は新しく作らない（平均30〜45字の目安は gemini-syntax.md 原則7）。

## 10. 「ここに説明が必要です」の書き方

- 置き場所は「書き手に確かめたい点」。形は `- ここに説明が必要です: 「TTL」（3段落目。原文と資料に説明がない）`。本文には入れない。
- 3点まで。確かめたい点の2点とは別に数える。多ければ、見出し、最初の段落、何度も出る語の順に選び、「ほかに N か所」と添える。
- 語ごとに説明の文案を書かない。説明は書き手が書く（output-format.md 7章）。
- expert には出さない。読者を決めないときも出さない。本文だけの指定でも出さない。
- 確かめたい点は、原文そのものの意味が決まらない所。説明が要る所は、書き手には分かっているが読者には足りない所。同じ語を両方に書かない。新規作成でも、資料に説明がなければ足さずに返す。

## 11. 読者像（ペルソナ）

- 「入社2年目の営業担当」「購買部の課長」のような読者像は、2つにだけ使う。3段階のどれに当たるかを決めること（読者像の分野と文書の分野が同じなら expert、違うが技術や業務の語に慣れていれば informed、それ以外は general）と、どの語に説明が要るかを決めること。
- 構成、敬語、常体と敬体、主張、例は、読者像で変えない。その人が知っていそうなことを推測して本文を変えない。
- 読者像は check に渡さない。報告の行に「general（指定。購買部の課長）」のように添えるだけにする。

## 12. 示し方

- 確認の記録の最初の行に `- 種類と読者: incident（推定）、expert（指定）` のように書く。決めなければ「決めていない」。指定と本文の形が食い違えば、行の終わりに短く添える。
- `--doc-type` と `--reader` を付けたときは、状態の行にも `doc_type=` と `reader=` が出る。確認の記録の行と食い違わないようにする。
- 決めた種類と読者だけを付ける。候補を減らすために種類を付けない。
- 推定したことや説明が要ることを、本文の中に書かない。本文だけの指定では、確認の記録ごと出さない。
- 利用者が種類か読者を直したら、新しい依頼として書き直し、check の run を `--new-run` を付けてやり直す（同じ実行のままだと、出力の1行目が「前回と同じ最終稿」や「修正後の検査」として、新しく見直し候補になった箇所を直さないよう案内する）。「直すのは1回まで」には数えない。

## 13. 種類と外す規則の全体の表

SKILL.md 4章で当てない範囲は、SKILL.md 1章の種類の表のとおり。lint が外す規則と根拠は次のとおり。

| 種類 | lint で外す規則 | 根拠 |
|---|---|---|
| pr | excess_list | 変更点と確認したことは並列が明確な箇条書き |
| article | なし | |
| incident | excess_list | 時系列の箇条書き。diff の文体の硬化の候補は参考としてだけ出る（「発生」「復旧」などの報告の語を開きすぎない） |
| proposal | なし | |
| minutes | bold_label_list、excess_list、sentence_end_repetition | 項目に分けた構造とラベルが普通。同じ文末の連続は議事録では人の文にも多い |
| manual | excess_list | 番号つきの手順は並列が明確な箇条書き |
| slides | bold_label_list、count_declaration、excess_list、short_summary_heading | 短い見出しと箇条書き、目次の数の宣言、まとめのページが普通の構成 |
| essay | なし | 読み取れる比喩を残し、成り立たない比喩を直すのは、エージェントが doc-types/essay.md に従って行う。metaphor_verb の候補（エッセイの比喩動詞）は外さない |
| formal | なし | 硬い語の言い換えと「〜を行う」の外枠は、エージェントが当てない（SKILL.md 1章の表）。diff の文体の硬化の候補は参考としてだけ出る |
| promo | emoji_prohibited、fragment_run | 書き手が気持ちや勢いを表す絵文字と、本文で評価の語を短く重ねる型（安い。うまい。早い。）は普通の書き方。「！」、見出しのキャッチコピー、勢いのある語と強める語は、エージェントが doc-types/promo.md に従って残す |

- lint は外した候補の件数だけを出す。中身は `--doc-type` を付けずに実行すると見られる。
- bold_not_rendered（表示されない太字）と metaphor_verb は、どの種類でも外さない。fragment_run（「速い。軽い。安い。」の型）は promo のときだけ外す（ほかの種類では外さない）。
- 差分、意味が変わる恐れ、資料との照合は、どの種類と読者でも同じ規則で出る。違うのは diff の文体の硬化と勢いの検査で、硬化は incident と formal のとき、勢いは pr、article、incident、manual、formal のとき、候補をすべて参考としてだけ出す。ほかの種類を指定したときも、勢いの絵文字の候補（promo を除く）と見出しの候補（promo と minutes を除く）は参考になる。種類を決めないときと promo は、どれも見直し候補のまま。promo では番号つき項目の行と太字だけの行も勢いの検査の見出しに数える（review-points.md）。読者では lint の候補も変わらない。

## 14. 例（合成）

| 元の文 | expert | informed（指定） | general（指定） |
|---|---|---|---|
| 青環境への切り替えで p95 が 120ms に下がりました。 | そのまま | そのまま。説明が要る所: 「青環境」 | そのまま。説明が要る所: 「青環境」「p95」（原文と資料に説明がない） |
| 資料: 「TTL はキャッシュを残す時間」。原文: TTL を 30 秒にしました。 | そのまま | そのまま（TTL は一般の技術語） | キャッシュを残す時間（TTL）を 30 秒にしました。（資料の定義の語で添えた。「変えたところ」に書く） |
