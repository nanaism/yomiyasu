# 技術記事・エンジニア発信向け仕様

技術記事では、手順や仕組みの説明を読み手が追えるように書きます。
[Qiita 7万件調査（逆瀬川 2026）](https://nyosegawa.com/posts/qiita-writing-before-after-ai/)を参考に、過剰な装飾を減らし、元の文や資料で分かる範囲で手順や設定を整理します。

---

## 1. 装飾と箇条書きの整理

### 太字と箇条書きの制限
太字は1,000文字あたり1〜2箇所までに抑え、段落内に複数の太字を乱発しません。残す太字は、かっこの内側だけを太字にするなど、表示される書き方に整えます（SKILL.md「装飾記号と不要な空白の排除」）。思考の流れや論理展開を箇条書きに頼らず、地の文の段落で記述します。
箇条書きを地の文に統合する際は、各項目を文書の立場に合う文末にします（SKILL.md「文書の立場と文末」）。元にない評価や義務（〜が大切です、〜する必要があります等）を足しません。単に並列された項目であれば箇条書きのまま残しても構いません。また、箇条書きを地の文にすると同じ文末が3つ以上続くときは箇条書きのまま残し、全体の15%以下の上限よりもこの規則を優先します。

### 装飾記号と定型構成の排除
見出しや本文に絵文字は使いません。装飾としての文末コロン（：）やダッシュ記号（—）も除きます。Qiitaの調査では「まとめ」見出しを含む記事が50%以上ありました。短い記事で本文を繰り返すだけの「まとめ」見出しは置きません。

## 2. 手順と設定を分かりやすくする

抽象的な概念説明にとどまらず、元の文や前後の資料にある情報の範囲で手順や設定を整理します。元の文にないコマンドやコード片を勝手に作って足すことはしません。

SKILL.mdの構造点検に従い、仕様の条件・例外・否定・限定が掛かる処理と、分岐・手順の順序を確かめます。語順の整理や文の分割を行っても、条件を別の処理へ広げたり、必要な用語の対応を崩したりしません。

| 不自然な比喩表現 | 客観的・具体的な記述への変換 |
|---|---|
| 設定を保存した瞬間に、古いキャッシュが静かに壊れます。 | 設定を保存するとすぐに、古いキャッシュが気づかないうちに使えなくなります。 |
| この調整が、検索の速さに地味に効いてきます。 | この調整が検索の速さに目立たないながらも役立ってきます。 |
| 原因調査に丸一日溶かしてしまいました。 | 原因の調査に丸一日かかってしまいました。 |
| この処理でデータの整合性を担保します。 | この処理でデータに矛盾が生じない状態を保ちます。 |

## 3. 文体

常体・敬体は、変更の指定がない限り原文を保ちます。技術記事という理由だけで敬体へ変えません。同一文末の連続は見直すきっかけにとどめ、語尾を散らすために文の働きを変えません。書き直しで新たに呼びかけを増やした場合は、各節の働きと文体変更の必要性を再確認します。
敬体にすることと、すべての動作を「〜します」にすることは別です。読み手への設計助言と、定められた手順、書き手の予定、道具の働きの説明を区別し、SKILL.md「文書の立場と文末」に従います。
「本稿では」「筆者は」といった過度な論文調や、冒頭の空疎な前置き（「近年、AI技術の発展は目覚ましく…」など）を削り、解決すべき課題や前提条件から書き始めます。
難しい漢語が続く箇所は、ふだん使う言葉や動詞に直します。漢字の割合は20%前後を目安にします。
