# yomiyasu

AIが書いた日本語の不自然な比喩、曖昧な主述関係、偏った構文を直し、読み手が「誰が何をどうしたか」を一読で追える文章にする。

- いちばん優先するのは、意味を保つことと、原文と資料にないことを足さないこと（4.1、4.2）。ほかの規則はこの範囲で使う。
- 直すのは文の組み立てと言い回し。表記の統一（送り仮名、漢字とかなの使い分け、数字や英字の全角と半角など）は直さず、表記の校正のスキルに任せる。
- すでに自然な文章は変えなくてよい。「変更は不要」も結果として認める。

## 1. 用途を決める

- 推敲: 原文がある。原文と資料にない事実は足さない。
- 新規作成: 資料から書く（資料が依頼文だけなら依頼文が資料）。資料にない事実は足さない。
- 原文と資料の両方があれば推敲として進め、資料も検査に渡す。

新規作成では、資料の書き方をそのまま写さず、依頼にある読み手と目的に合わせて書く。書いたあとは資料と読み比べ、主張、条件、担当、数値、未確認の事項が資料どおりかを確かめる。

あわせて次の3つを決める。

- 文書の立場: 勧め（読み手に勧める・頼む）、決まり（ルール、手順、仕様）、説明（事実、結果、考え）。依頼にある行き先と読み手を先に見て、次に本文の手がかり（主語、宛名、見出し）で決める。種類の名前だけでは決めない。決まらなければ決めずに進める。
- 文書の種類: 下の表の10種類。当たらなければ決めない。
- 読者: expert（同じ分野の専門家）、informed（分野は違うが技術に詳しい人）、general（専門知識のない人）。読者像を渡されたら近いものにする。

種類と読者は指定に従い、なければ行き先と本文の形から推定する。自信がなく、決め方で直し方が変わるなら、書き直す前に1回だけ確かめる。確かめられないとき（本文だけの指定、一回きりの実行、ほかのスキルの途中、質問しないでと頼まれたとき）は決めずに直す（細部は `references/audience.md`。informed か general を指定されたときは読む）。

- expert: 用語を残し、説明を足さない。
- informed（分野の外で通じにくい語）と general（説明のない用語）: 指定されたときは、原文と資料にある説明で言い換えるか添える。推定のときと、説明がないときは、語を残して「書き手に確かめたい点」に「ここに説明が必要です: 語（場所）」と書く（2点とは別に3点まで）。
- 識別子が主語の文は、expert と informed には直さない。見出しと節の数と順は、どの種類と読者でも変えない。

| 種類 | 当てない4章の規則（範囲） |
|---|---|
| pr（PR説明） | 過剰な箇条書き（変更点、確認したこと） |
| article（技術記事） | なし |
| incident（障害報告） | 過剰な箇条書き（時系列）、硬い漢語（発生、復旧などの報告の語） |
| proposal（提案書） | なし |
| minutes（議事録） | 過剰な箇条書き（太字のラベルを含む） |
| manual（マニュアル） | 過剰な箇条書き（番号つきの手順） |
| slides（スライド） | 過剰な箇条書き（太字のラベルを含む）、数の宣言、繰り返すだけの「まとめ」、体言止めの項目での主語の抜けと文末 |
| essay（エッセイ・小説） | 読み取れる比喩（エッセイでも「効く」の類は直す）、小説のコピー調とダッシュ |
| formal（公用文、規程、契約書、仕様書） | 硬い漢語（正式な語）、「〜を行う」「〜することができる」の外枠 |
| promo（紹介記事・宣伝文） | 見出しのキャッチコピー、「！」と絵文字、勢いのある語と強める語 |

## 2. 手順

1. 種類を決めたら `references/doc-types/<値>.md` を読む。決めなければ、分野が決まったら `references/domains/` の該当するファイル（tech.md、business.md、essay.md）を読む。
2. 原文（新規作成なら資料）の各文の主張、比重、言い切りの強さ、文の働き（事実、意見、依頼、例え、皮肉、仮定、伝聞）を内部でメモする。新規作成では、資料の主張、条件、担当、数値、未確認の事項も書き出す。メモは出力しない。
3. 4章に従って書き直す。メモした点は変えない。4章の型に当たった箇所は、直す前に案を1つ書き、原文と6点（何について述べるか、何を認め何を否定するか（否定対比は4章の表）、誰が誰にするか、範囲と条件、断定・推量・伝聞の強さ、数値・固有名詞・時期）を比べる。1つでも変われば案を捨てて原文を残し、「残したAIっぽいところ」に書く（言い直しテスト。例は `references/rephrase-test.md`）。資料に基づいて訂正や補足をしたら、「変えたところ」に「（資料に基づく補足）」と書く。迷ったときだけ次を読む。
   - 文末を直す、変更報告や今の方針を書く、立場が決まらない: `references/stance-and-endings.md`
   - 主述、修飾、つながり、文の分け方、見出し、コピー調、記号と太字: `references/gemini-syntax.md` の該当する原則
   - 語の言い換え（比喩、流行語、大げさな名詞、前置き、結び）: `references/slop-catalog.md`
   - 情報が足りない、説明の欄や確かめたい点の書き方: `references/output-format.md`
4. 最終稿を原文とは別のファイルに保存し、検査する。
   `python3 <スキルのディレクトリ>/scripts/yomiyasu_check.py run --source 原文 --final 最終稿`
   - 資料があれば `--material 資料` を足す（何個でも）。新規作成では `--source` の代わりに `--material` を渡す。
   - 文書の立場が決まっていれば `--stance 勧め`（または 決まり、説明）を、種類を決めたら `--doc-type 値` を、読者を決めたら `--reader 値` を足す。
   - `python3` がなければ `python` か `py -3` で実行する。
5. 出力の1行目に従う。候補は直す指示ではなく、原文と資料に照らして確かめる箇所。見方に迷ったら `references/review-points.md` を読む。直すのは1回まで。直したら4のコマンドをもう一度実行する。そのあとは本文を変えない。
6. 原文のファイルを更新する依頼なら、最終稿をそのまま原文の場所に写す（中身は変えない）。
7. 提出（ファイルの保存、PR本文への貼り付け、返答）の直前に、本文を変えずに1回確かめる。
   `python3 <スキルのディレクトリ>/scripts/yomiyasu_check.py verify --final 提出するファイル`
   1行目が「ハッシュが記録と合いました」を含まなければ、本文を変えずに4と7を1回だけやり直す。それでも合わなければ、最終稿の照合を実行しなかった検査として報告する。
8. 完了報告を書く（3章）。

- `<スキルのディレクトリ>` は、このファイルがあるディレクトリ（Claude Code では `${CLAUDE_SKILL_DIR}`）。
- ファイルを作らない対話では、4を下の `run --stdin` にする（資料は `<<<yomiyasu:material>>>` の行のあとに置く）。返答の本文は渡した最終稿と同じにする。6と7は行わない。

```bash
python3 <スキルのディレクトリ>/scripts/yomiyasu_check.py run --stdin <<'YOMIYASU_EOF'
<<<yomiyasu:original>>>
（原文）
<<<yomiyasu:final>>>
（最終稿）
YOMIYASU_EOF
```

- Python やコマンドを実行できないときは、4〜7の代わりに、原文と最終稿を `references/review-points.md` 4章の観点で読み比べる。この点検は検査を実行したことにならない。

## 3. 完了報告

返答は次の形にする。説明の欄は機械的に並べない。

```markdown
### 書き直した本文
（読み手に渡す本文。書式は保ち、コードの囲みに入れない。原文の「未定」「調査中」は残し、推敲側の注記や質問は入れない）

### 変えたところ
- 元の表現 → 書き直し後の表現（理由）
（意味が動きやすい変更、つながりを直した所、文末をそろえた所（1行にまとめる）、補った語だけ。5点まで。残した箇所は書かない。なければ「なし」）

### 残したAIっぽいところ
（4章の型に当たったが、言い直すと意味が変わるので残した表現と理由を1行ずつ。なければ見出しごと出さない）

### 書き手に確かめたい点
（本文を確定するのに要るものだけ、2点まで。何が読み取れないかを短く述べ、中立に尋ねる。なければ見出しごと出さない）

### 確認の記録
- 種類と読者: （例「incident（推定）、expert（指定）」。決めなければ「決めていない」）
- 実行した検査: （lint、diff、資料との照合、最終稿の照合 のうち、実行したものだけ。なければ「なし」）
- 実行しなかった検査: （なければ「なし」。あれば「検査名（理由）」）
- 硬化の検査: （run の出力の「硬化の検査:」の値を写す。なければ書かない）
- 勢いの検査: （同じ形）
- （verify の出力の2行目をそのまま写す。ファイルを作らない対話では run の出力の2行目。実行できなかったときは `yomiyasu-check: not_run reason=no_python` のように書き、理由は no_python、not_allowed、check_error から選ぶ）

（エッセイ、小説、紹介記事と判断して表現を残したら、判断を1行で書く）
```

返答そのものが納品物で本文だけを返す指定があるときは、確認の記録も説明の欄も付けない（検査は同じように行う）。納品物がファイルで、返答が別にあるときは返答に付ける。ファイルを作らない対話では、「実行しなかった検査」に「最終稿の照合（ファイルを作らない対話のため）」と書く。

- すでに自然で変えなかったときも run と verify は実行する。
- 原文を渡された依頼では、状態の行が `mode=rewrite` になる。`mode=compose` なら原文を `--source` に渡していないので、4からやり直す。

「yomiyasu で整えた」のように手順全体を終えたと読める書き方は、実行しなかった検査が「なし」のときだけにする。検査を実行したことは、意味が保たれたことや読みやすさの合格を示さない。

## 4. 書き直しの規則

### 4.1 最優先: 意味を保つ

書き直す前後で次の4点を同じにする。

1. 主張: 論点を別の概念にすり替えない（「本質」を「目的」にしない）。動詞を足して論点を変えない。
2. 比重: 否定していたものを並べたり（Aに加えてB）、順位を変えたりしない。何と何を比べているかも保ち、分からなければ元の表現を残す。重要さの評価を、頻度や見落としやすさの評価に変えない。
3. 言い切りの強さ: 断定は断定のまま、推量や可能性はその強さのまま書く。
4. 文の働き: 評価は評価、説明は説明、依頼は依頼のまま。実施済み、現在、予定を書き分け、完了した変更を予定の形にしない。

数値、日付、名前、否定、条件、例外、確度、実施済みと未確認の区別も変えない。

文の働き（手順2の7つの種類）は、メモと書き直した文を読み比べて確かめる。次の書き換えはしない。

- 伝聞（〜とされる、〜らしい）を断定にする。意見（〜と思う）を事実として言い切る。
- 依頼を説明や予定にする。仮定（予算が通れば始められる）を予定にする。
- 例え（まるで戦場のようだ）を「戦場だ」と言い切る。反語をただの疑問にする。

種類は文が何を述べているかで決める（比喩動詞を含む「休日を溶かした」は事実の文）。例えの文は例えのまま残すのが基本で、例えの語を外すときも、例えが伝えていた中身を同じ強さで書く。皮肉や反語は、文脈から確定できるときだけその種類にする。文を分けたりつないだりしても、元の各文の種類をどこかで保つ。決めきれない文は候補を残したまま扱い、元の種類に戻せなければ原文を残して「書き手に確かめたい点」に出す。小説や人文系の文章で書き手が残した複数の読みは、一つに決めない。

### 4.2 足さない

- 根拠にするのは、原文、依頼、提供された資料だけ。本文にも説明の欄にも当てはめる。
- 分からない動作主、担当者、行動、原因、条件、数値、例、専門用語、書き手の気持ちを推測で足さない。元にない五感の描写、教訓、読んだあとの効果（業務効率が向上します）も足さない。
- 書き手がAIに出した指示や除外の判断（今回は一般論ではなく体験に絞って紹介します、この記事では〜は扱いません）を本文に残さない。除外を述べる文は削る。読者のために扱う範囲を示す文（マニュアルの対象範囲など）は残す（`references/slop-catalog.md` 6章）。
- ぼかした語を、より狭い具体的な事実に置き換えない。前後の文にある限定を、限定のない文へ持ち込まない。
- 出典のない「〜という声もあります」は、声の主や数を補わず、強さも変えずに本文に残す。
- 要約を頼まれていなければ情報を省かない。要約するときも、残す主張の条件、例外、確度は保つ。
- 提供された定義、識別子、値と状態の対応は、読み手に要るなら説明に使う。必要な情報を削って短くしない。
- 情報が足りず確定できないときは、元の主張、条件、未定の状態を本文に残し、確認は「書き手に確かめたい点」で行う（`references/output-format.md`）。本文の途中や末尾に「要確認」などの編集の印を挟まない。

### 4.3 直す範囲と文末

- 直すのは、読み違いや関係を追う負担を特定できた箇所だけ。変更は問題の近くに絞り、元から自然な箇所は残す。
- 文を切る、つなぐ、語順を変えるときも、条件、否定、因果、時系列、比重が掛かる範囲を保つ。書き手が見聞きした日時と、出来事が起きた日時を取り違えない。
- 説明文では、見出しや問い、列挙の前置きが「何を説明する」と言っているかを全文で一度確かめ、本文の対応が追えるかを見る。分からない対応は推測で書き足さず、「書き手に確かめたい点」に出す。
- 文末は、文書の立場と各文の働きで選ぶ。文書の目的をそろえることと、すべての文末を同じ種類にすることは別。
- 変更報告では「どの指針・設定・実装を、どう改めたか」を書き手の行為として述語まで書く。変更と分かる内容だけを変更として書き、改定前が分からなければ比較や追加を作らない。
- 今の方針は「〜するようにしています」「〜する方針です」のように、誰の方針かが読める形にする。システムの動作（返します）、できること（できます）、依頼、予定はそれぞれの形のままにする。
- 同じ立場の中の強さ（〜しましょう と 〜してください）は変えない。期限や必須の指示を弱めない。常体と敬体は原文か指定に従う。

### 4.4 核の規則

| 型 | 直し方 | 残す場合 |
|---|---|---|
| 比喩動詞（倒す、効く、溶かす、潰す） | 4.5 のとおりに書く。含み（うっかり、ようやく、〜てしまった、地味に）は別の語で残す（丸一日溶かした → 丸一日かかってしまった） | 定着した慣用句（骨が折れる、手を焼く）。意味を保てる言い換えがないとき |
| データやシステムの「壊れる」、「静かに」「黙って」 | 「おかしくなる」「使えなくなる」「気づかないうちに」のように同じ広さの語にする | 機械や身体の文字どおりの「壊れる」。整合性やエラーなしの話と明らかなときだけ「整合性が失われる」「エラーを出さずに」 |
| 道具や概念の擬人化（コードが語る、ジョブが声を上げる）、抽象名詞が人の判断を動かす書き方 | 内容の所在を書く。誰の行動か分かるときだけその人の行動にする。条件や「できる」を足さない | 働きが一読で分かる言い方（このツールはログを集めます、ワーカーが目を覚ます） |
| 主語、目的語、指す先の抜け | 原文と資料で確定した主体と対象だけを補い、「変えたところ」に出す。述語ごとに誰の動作かを確かめ、主体が変わる所は書く | 主体が分からないとき。システムの動作を人の行為にしない |
| 「〜を行う」「〜することができる」の外枠 | 対象と動詞を直接つなぐ（値を代入する）。義務、可能、評価は保つ | 確認済みの結果（一致していることを確認した）。条件が変わる言い換え（代入しない処理を false の代入にしない） |
| 中身のない前置き（重要なのは、結論から言うと、正直に言うと） | 削るか、評価を述語に移す（重要なのはデータ構造です → データ構造が重要です） | 理由、対比、結論、方針への切り替えを担うもの（比較から方針へつなぐ「結論として」） |
| 文頭の「もちろん、」に数語だけが続く短い文 | 「もちろん、」を外し、別の語で補わない。認めた内容と程度は残す | 会話や引用、問いへの答え、条件の確認、後に具体的な内容が続く文、「AはもちろんB」 |
| 否定対比（AではなくB）と否定の重ね | Aを消しても主張が同じときだけ、Bだけを言う文にする。Aを肯定の文へ移さない | 比重を担う否定（思い込みや外れた仮説を正すもの）。「〜ではなく、〜でもある」は一文のまま。問いの二つを打ち消すだけなら「どちらでもない。」と短く受けてよい |
| 予告だけの文、数の宣言（次の点が挙げられます、ポイントは3つです） | 予告の重みを述語に残し、中身の文と1文にする | 長い説明の案内。宣言の数と項目の数が合わなければ変えずに確かめる |
| 言い直しの締め（まとめると、要するに）、繰り返すだけの「まとめ」 | 削る。そこにしかない数値、条件、例外は本文に移す | 新しい情報や絞り込みがあるもの、長い文書の要約。決意や抱負の結び（4.5） |
| 定型の結び、チャット応答の名残（いかがでしたでしょうか、ご質問ありがとうございます） | 削り、本文の自然な結びで終える | 手紙やメールの挨拶、チャットの返信そのもの、書き手の実際の申し出 |
| 接続語や文頭の指示語のずれ、続く「また、」、因果の読めない「これにより」 | 何と何をつなぐか確かめて合う語にする。外しても関係が変わらない「また、」「さらに、」は外す | 因果が読める「これにより」。逆接、理由、条件、例外の接続。分からなければ直さず確かめる |
| 立場に合わない文末（助言が予定の形、決まりが「〜しましょう」、完了した変更が予定の形） | 合わない文末だけを直し、「変えたところ」に1行でまとめる | そろっていて立場に合う文末。同じ立場の中の強さの違い。指定のない常体と敬体の切り替え |
| 大げさな名詞（契約、正本、ゲート、台帳、仕組み、境界） | 実際の役割に合う語（ルール、原文、確認、記録など）にする | 取引の契約、正式文書の正本、品質ゲート、会計の台帳、境界値。指す先が分からなければ語と条件付きの主張を残して確かめる |
| 意味のぼやけた流行語と未定義造語（解像度、腹落ち、手触り、意思決定OS） | 原文から分かる範囲で、ふだんの言葉か機能の説明にする | 文書の中で定義された用語、字義どおりの用法（データの粒度）。中身が分からなければ残して確かめる |
| 直訳の語と専門用語（版、回帰、閉包、旗） | その分野で定着した用語にする（バージョン、リグレッション、フラグ） | 定着した言い方（第2版、回帰テスト）、画面の項目名、識別子、表やAPIの名称とキー |
| 硬い漢語、決まり文句、根拠のない誇張（活用する、実施する、シームレス、圧倒的） | 「使う」「行う」にする。何がどう変わるかが原文にあればそれを書く | 正式な用語、製品名、数値の裏付けや書き手の実感がある誇張。報告書に合う語（4.5） |
| 体験を大げさにする熟語と教訓化（真理、深淵、虚飾） | 素朴な言葉で、元の体験と気持ちを書く | 書き手が実感として使っている語 |
| コピー調（「資料を、全員へ。」「速い。軽い。安い。」） | 確定した対象と評価や動作を述語までつなぐ | 対象が確定しないとき。小説や随筆の語り。紹介記事。引用 |
| 装飾記号（絵文字、文末コロン、ダッシュ、意味の重なるカッコ、強調だけのカギ括弧） | 外して句読点や助詞でつなぐ。ダッシュを外すと理由や条件の掛かりが広がるなら2文に分ける | ラベルと値のコロン（日時：10時）、罫線の区切り線や図、出典、小説や随筆のダッシュ、引用。原文の「■」「・」は Markdown の記号に置き換えない |
| 過剰な箇条書き、太字のラベルとコロンの箇条書き | 論理を分断している箇条書きは地の文にする。ラベルの語を文に含める | 並列が明確な箇条書き（変更点、手順、担当と結果）。地の文にすると同じ文末が続くとき |
| 読みにくい長い文と読点 | 読み違いを特定できた所だけ、つなぎ言葉で関係を残せるときに分ける。役割のない読点を外す | 長いだけの文。目的や理由が文末に掛かる文。主題と動作主を分ける読点（会議では、担当者が説明しました） |
| 案内にならない見出し（文を詰め込む、「〜とは：」） | 何を扱うか分かる短い項目名にし、外した警告や条件は本文へ移す | 見出しで警告を伝えると依頼で明示されたとき。数と番号の対応。文書の種類のラベル（議事録：10月定例会） |

### 4.5 人の比較で好まれた書き方

- 書き手の決意や抱負を述べる結び（〜に取り組んでまいります、これからも〜作っていきたい）は削らない。内容を残し、大げさな語だけを直す。
- 比喩動詞は、何がどう変わったかを書く（おかげで少しずつ変わってきている）か、定着した言い方（少しずつ薬になっている）にする。「じわじわ効いている」を残したり、「じわじわ助けになる」「良いほうに働いている」のように効き目や評価だけをぼんやり述べたりしない。
- 「ます。」で短い文に区切りすぎない。
- 主題のすぐあとに間を作るだけの読点（「応答は、〜」）を付けない。
- 議事録や報告では、出席者、発言者、作業した人、担当を引き受けた人を区別する。担当が書かれていないことを「担当未定」と決めない。
- 報告書では「障害が発生した朝」のように、文書の種類に合う語を残す。ふだんの言葉に開きすぎない。
- 和文と英数字の間の空白を、一律に足したり消したりしない。
