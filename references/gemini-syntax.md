# 自然な日本語への構文変換原則

本ドキュメントは、AIが生成した文章に特有の不自然な日本語構造を解体し、人間が引っかかりなく読める文体へ変換するための構文変換規則である。
学術研究、計量コーパス分析、コミュニティの知見に基づき、科学的根拠を持って体系化した。

---

## 学術研究および計量分析に基づく知見

本スキルの構文変換規則は、以下の調査研究から得られた実証的知見を基礎としている。

### 1. フォーマットバイアスの構造的解明（Zhang et al., ACL 2025）
強化学習（RLHF/DPO）の報酬モデルは、文章の質とは独立して太字、箇条書き、絵文字を好むバイアスを持つことが知られている。このバイアスによりAIは過剰な装飾記号を出力するため、客観的な基準で制限することが不可欠となる。

### 2. 日本語文章平易化の4基準と漢字過密の課題（Yamashita et al., LREC 2026）
文章の平易化には「必要性」「十分性」「文レベルの平易さ」「文書レベルの平易さ」の4基準が重要とされる。特に漢字の密集（漢語の連続）や長大な複文は可読性を著しく損ねるため、文長を30〜45文字に保ち、難解な熟語を自然な動詞や和語へ開く作業が効果をあげる。

### 3. 意味保持と不要な情報増補の防止（Jeong et al., ACL 2026 / Ide et al., 2026）
文章を平易化・脱臭する際、技術的制約や数値、条件分岐を勝手に脱落させてはならない。また、AIがリスク回避のために勝手に付け足す一般的な免責事項や大げさな前置きを排除し、原文の意図と事実関係を正確に維持する。

### 4. 働きかけ・要請表現における自然な距離感（Chen et al., Discover Education 2025）
AIは呼びかけ語や形式的な敬語クッションを過剰に付加し、自然な日本語話者の表現から乖離しがちである。本スキルでは、動作主と文の働きを確かめてから語調を整える。依頼か説明か決まらない場合は、原文を保ち、本文を確定するために必要な点だけ書き手に確認する。

### 5. 計量文体論と流暢さの罠（Zaitsu et al., PLOS ONE 2025 / 三浦・久保山, JSAI 2026）
人間はAI特有の表層的な流暢さに惑わされやすいものの、助詞配置や文末の連続（「〜です」が3文続くなど）に機械的な偏りが生じる。文末の種類（勧め・決まり・説明）は変えずに、画一的な文末を崩してリズムに多様性を持たせることが肝要である。

### 6. Qiita 7万記事の計量分析（逆瀬川 2026）
AI普及後に生じた形式のインフレ（太字3倍、箇条書き1.8倍、読点間隔の短縮、ダッシュ記号の10倍増）と、抽象化による手順の希薄化が実証されている。これらを抑制し、読者が行動できる具体的な記述へ復元したい。

### 7. 統語構造（SVOCM）の復元とAI語の解剖（nasuvitz / ktrmnm 2026）
AI文章の不自然さの本質である主述関係の破綻、非生物主語、セルフラベリング、不要な否定対比を解消する論理的枠組みを提供している。

## 構文変換のコア原則

### 原則 1: 動作主・対象・動作の明確化

言い換える前に、主語と述語、修飾語と掛かる先、指示語と指す対象を確かめる。原文から確定した関係を読み手が追えるように整理し、未確定の関係は確定させない。省略や受動態そのものを不自然とはみなさず、文脈から関係が伝わる箇所は残す。

動作主（S）の明示として、元の文や前後から分かる範囲で処理や判断を行う主体を置く（分からない場合は勝手に動作主を創作して足さない）。省かれた目的語や対象を補うのは、前後の文にその語があるときだけに限定する。指示代名詞（O）の実名化として、「これ」「片方」の指す先が文脈から分かるときに限って具体的な名詞に置き換える。動詞（V）の具体化として、抽象的な表現を避け、何がどう変化するのかをふだん使う平易な動詞で直接記述する。
元から「もの」「それら」で処理や選別の対象を省いている場合も、対象が確定し、前の文から拾い直す負担があるなら、原文の名詞を再掲する。名詞が近くにあることだけで対象を選ばず、複数候補を一つへ狭めない。
語が既出でも、語どうしの関係が同じとは限らない。助詞・修飾の位置・述語を変えるときは、対象と扱い、実行と待機の主体、修飾先を原文と照らし合わせる。「XをYとして登録」と「XのYを登録」のように、使う語が同じでも対象が変わる場合がある。同じ関係と確定できなければ原文を保ち、書き手に確認する。
原文と改稿の両方で、述語を中心に語句を分け、主語・対象・扱い、修飾語→係る先、指示語→指す対象を短く対応づける。名詞句の修飾を担当者の動作へ移す場合は、意味が同じと確認できる根拠が要る。「独立した展示」を「独立して担当する」へ変えるように、修飾するものを移さない。文書の話題だけで修飾先を確定せず、複数の読みが残れば原文を保って確認へ出す。語形を変えても意味が保てる場合は整理してよいが、矢印が引けること自体を等価性の証明にはしない。
主述や使役の対応を直すときは、まず原文の動詞を保って、確定した主語・相手・対象を明記する案を検討する。動詞自体を直す理由がないのに、対象を補えば伝わる文を別の長い構文へ組み替えない。
動詞を平易に言い換えた後も、文全体の語順を確かめる。仕事の通知を表す「連絡が担当者に飛ぶ」を直す場合、「担当者に連絡が届く」のように、受け手を先に置き、主語と述語を追いやすくする案も検討する。主述を近づけるために修飾先や条件の範囲を変えず、元から自然で関係が追える語順は残す。

| 確認する表現 | 整理した表現 | 解説 |
|---|---|---|
| 両者を突き合わせることで、差分が浮き彫りになる。 | 両者を比べると、違いがはっきり分かる。 | 元にない名詞を足さず、「浮き彫りになる」の含みを「はっきり分かる」に残す。常体も保つ。 |
| 処理を流すたびに、状態が勝手に書き換わっていく。 | 処理を流すたびに、意図せず状態が書き換わっていく。 | 「勝手に」の不本意な含みを「意図せず」に残す。「流す」の指す処理は文脈なしに限定しない。 |
| 使い倒すことで、道具が手に馴染む。 | 徹底して使い込むことで、道具を思い通りに扱えるようになる。 | 「使い倒す」と「手に馴染む」の含みを平易な言葉で残し、常体も保つ。 |
| 前後を取り違えると、意図しない挙動につながる。 | 前後の順序を間違えると、意図しない動き方につながる。 | 「挙動」を平易にし、原因と結果の関係、常体を保つ。 |

### 原則 2: 文書の立場に合わせた文末の統一

日本語では主語が省略されることが多く、文末の形が動作主や文の働きを伝える。誰が誰に何のために書くかを手がかりに、各文・各節の助言・決まり・予定・説明・評価を区別する。文書全体へ同じ種類の文末を当てない。常体・敬体は別に判断し、変更指定がなければ原文を保つ。
ただし、文書内で文末がそろい、動作をする人と文の働きが依頼や本文の手がかりに合っている場合は文末を変更しない。そろっていることだけでは適切な立場だと判断しない。「まず」「次に」「最後に」は順序を示し、動作をする人や文の働きを決める語ではない。読み手への助言なら勧めの形にし、定められた運用手順、書き手の予定、客観的な処理・操作の説明は、それぞれの働きに合った文末を残す。
説明文の客観的な言い切りを、勝手に可能表現（〜できます）に変えない。提案を、勝手に依頼に変えない。依頼か説明か決まらない場合は、原文を保ち、本文を確定するために必要な点だけ書き手に確認する。不明な働きを「〜してください」や「〜できます」で確定させない。
相手との関係や書き手の希望が分かる依頼は、内容・条件・期限を保って語調を整える。希望された依頼の定型と、新しい具体的な便益・感情・感謝の追加を区別する。定型を一律に追加・削除せず、安全手順や必須の指示を弱めない。「ください」だけで命令口調と判定しない。

| 混在・不自然な表現 | 立場に合わせた表現 | 解説 |
|---|---|---|
| 会議の前に資料を共有しておきます。事前の確認を心がけましょう。（※読み手への助言・心得の文書） | 会議の前に資料を共有しておきましょう。事前の確認を心がけましょう。 | 読み手に勧める文書のため、書き手の方針のような「〜しておきます」を勧めの文末へ統一する。 |
| パスワードは定期的に更新しましょう。安全性を保つことが重要です。（※チームの運用ルールの文書） | パスワードは定期的に更新します。安全性を保つことが重要です。 | 運用ルールの文書のため、勧めの文末を決まりの「〜します」へそろえる。決まりの理由を述べる文（〜ことが重要です）はそのまま残す。 |

### 原則 3: 非生物主語（擬人化）の解体

道具や概念に感情や意志を持たせている擬人化表現（「コードが語る」「システムが願う」等）に限り解体する。道具や仕組みの働きを客観的に述べている文（「このツールは通信ログを収集します」等）はそのまま残す。
直す場合も、元にない条件（「〜を使えば」）や可能（「〜できます」）を勝手に足さず、客観的な事実として記述する。

| 確認する表現 | 整理または保持する表現 | 解説 |
|---|---|---|
| このドキュメントが、APIの仕様を語っている。 | このドキュメントに、APIの仕様が書かれている。 | 内容の所在として書き直し、常体を保つ。 |
| 新しいガイドラインが、チームに変化を促す。 | 新しいガイドラインが、チームに変化を促す。 | 作用の説明として保持する。実際に変化が進んでいるという出来事へ変えない。 |
| コードが自らの振る舞いを証明する。 | コードが自らの振る舞いを証明する。 | 「証明」が何を指すかを文脈で確かめる。非生物主語だけを理由に「示す」へ弱めない。 |
| 画面の配置が、利用者の迷いを誘う。 | 画面の配置が、利用者の迷いを誘う。 | 原因と結果の説明として保持する。配置が分かりにくいという評価や、状況が変化したという情報を足さない。 |

### 原則 4: 比喩動詞の具体化とふだん使う言葉への変更

近年のAIが好む「倒す」「効く」「溶かす」「潰す」といった比喩表現を、難解な技術用語や硬い漢語に寄せるのではなく、ふだん使う言葉に戻す。
比喩や言い回しが持っていた「含み（気持ちや評価の向き）」は必ず残す。
- 含みの例: 「うっかり」の不注意、「ようやく」の待ちくたびれた感じ、「〜てしまった」の後悔、「地味に」の目立たないけれど確かにある感じ。
- 比喩の語は言い換えてかまわないが、その語が伝えていた含みや理由は、別のふだんの言葉で補って言い表す。
- 比喩動詞だけでなく、副詞や前置きの言い回しも同じ扱いとする。

データやシステムに対して使われる「壊れる」はAI特有の直訳・比喩のため、「おかしくなる」「使えなくなる」のように、意味の広さが同じふだんの言葉に改める。「データの整合性が失われる」「不整合が生じる」のように専門用語にするのは、元の文や前後から明らかに整合性の話だと分かるときだけに限定する（元の文の言い切りの強さは弱めない）。時計や機械など物理的な物体や、身体（お腹を壊す等）の文字どおりの「壊れる」はそのまま残す。「静かに」「黙って」のようなぼかしは、「気づかないうちに」「知らないうちに」のように気づけない幅のまま書く。「エラーを出さずに」「通知なく」のように仕組みの話として書くのは、元の文や前後から、エラーや通知が出ないことがはっきり分かるときだけにする。

「骨が折れる」「手を焼く」「目から鱗が落ちる」「首を長くして待つ」のような、ふだんの日本語で定着した慣用句は、AIっぽい比喩として扱わず、そのまま残す。業務仕様でも、意味を取り違えるおそれがなければ残す。迷ったときの目安は、その言い方を、AIが広まる前の人の文章でもふつうに見かけるかどうか。見かけるなら残す。

| 比喩表現 | 自然で直接的な表現への置き換え | 解説 |
|---|---|---|
| 例外が起きたときは、安全側に倒す。 | 例外が起きたときは、安全を優先する。 | 「倒す」を平易にし、元にない処理内容は補わない。常体も保つ。 |
| この工夫が、後々の運用で地味に効いてくる。 | この工夫が、後々の運用で目立たないながらも役立ってくる。 | 「地味に」の含みと、後々役立つようになることを残す。条件や余計な強調語は足さない。 |
| 古いコードの問題を1つずつ潰していく。 | 古いコードの問題を1つずつ直していく。 | 「潰す」を平易な動詞に直し、常体も保つ。 |
| 通信が切れた瞬間に、画面が静かに固まる。 | 通信が切れた瞬間に、気づかないうちに画面が動かなくなる。 | 「静かに」を気づけない幅のまま直し、出来事のタイミングと常体も保つ。 |
| 設定の反映に丸一日溶かしてしまった。 | 設定の反映に丸一日かかってしまった。 | 後悔の含みと常体を残して平易に記述する。 |

### 原則 5: セルフラベリングと否定対比の整理

AIは「重要なのは」「結論から言うと」といった不要な前置き（セルフラベリング）や、否定対比の構文を好む傾向がある。
前置フィラーを削ってよいのは、削っても主張が変わらないときだけである。「重要なのは」「大事なのは」が「何が大事か」という評価そのものを担っているときは、評価を消さずに述語に移して残す（「〜が大事です」「〜が重要です」）。
理由・対比・結論や、説明から方針への切替を担う前置きも保護する。比較結果を採用方針へつなぐ「結論として」などは、他の語から同じ関係が読めなければ削らない。
否定対比（AではなくB）は、否定を外しても主張が変わらないときだけ肯定文にする。Aだと思われがちなところをBだと言い直しているような、意味や比重を担っている否定は、否定を残したまま言い回しだけを自然にする。否定していたAを「Aに加えてB」と並べたり、「AよりB」と順位づけしたりしない。否定を残すときに、元にない理由の文や勝手な強調語（「そのもの」等）は足さない。

| 不自然な例（前置き・対比） | 自然な表現 | 解説 |
|---|---|---|
| 結論から言うと、このボタンを押すだけで完了します。 | このボタンを押すだけで完了します。 | 単なる前置きは削り、本題から直接書く。 |
| 重要なのは、画面の見た目ではなく裏側のデータ構造です。 | 画面の見た目ではなく、裏側のデータ構造が重要です。 | 評価（重要）を述語に残し、否定対比を保つ（「そのもの」等は足さない）。 |
| 目的は、機能の追加ではなく使いやすさの向上です。 | 機能の追加ではなく、使いやすさを高めることが目的です。 | 否定対比が方針の切り替えを示しているため、否定を残して表現を整える。 |

### 原則 6: 意味保持（Semantic Preservation）と不要な情報増補の防止

Jeong et al. (2026) および Ide et al. (2026) が指摘するように、脱臭や平易化において最も注意すべきは「原文の意味や制約を壊さないこと」である。パラメータ、バージョン要件、例外条件などの技術的制約や前提条件は勝手に削らない。同時に、原文にない動作主、名詞、行動、原因、条件、数値、例、専門用語を勝手に足さない。
元の文が言い切っていることは言い切ったまま、推量や可能性で書いていることはその強さのまま保つ（「おそれがあります」と弱めたり、「〜と言えるでしょう」を断定に上げたりしない）。文の働き（評価・説明・依頼・予定・感想）も変えずに維持する。
文脈から特定できない情報は本文で勝手に補わず、出力の「書き手に確かめたい点」として提示する。「一般に〜」「現代社会において〜」「もちろん〜とは限らないが」といったAI特有の無意味な包装紙を削り、事実のみを残す。

### 原則 7: 呼吸に合った文長（拍）と読点・漢字過密の抑制

Yamashita et al. (2026) は長文や難解語に対するLLMの評価バイアスを指摘している。これを受け、本スキルでは実務上の編集目安として平均文長30〜45文字を推奨基準に設定している（※この字数範囲は本スキルの運用目安であり、論文中の実験数値ではない）。60文字を超える長大な複文は分割を検討する目安とするが、文が長いことだけを理由に分けることはしない。長い文を分けるのは、前後のつながり（手段・理由・順序・対比）を、後ろの文のつなぎの言葉（「そのため」「こうすることで」「一方で」「反対に」など）で残せるときだけに限定する。目的や理由が文末の結論にかかっている文（例: 「設定を先に読み込んで、起動を速くするために使います」のような、〜するために〜です／〜しますの形）は、分けると「何のために何が必要か」の向きが変わりやすいため分けない。分けると向きが変わるなら分けずに残す。極端な短文（10文字未満）を連打して劇画調に仕立てる手法も避ける。1文あたりの読点は0〜2個を目安にし、不自然な位置や掛かり先を読みにくくする箇所を調整する。元から読みやすい文の読点を、数や見た目だけで削らない。文頭の不自然な強調読点（「前提を、〜」「ここでは、〜」など）は打たない。漢語が連続して硬くなった箇所は、平仮名や動詞へ適度に開いて読みやすさを確保する。

### 原則 8: 文末の画一化排除と流暢さの罠の回避
Zaitsu et al. (2025) および三浦・久保山 (2026) が指摘するように、AIは表面的な流暢さの裏で文末や構文を画一化させる。
ただし、文末のリズム調整は、AIっぽさを直すついでに同一文末（「〜です」「〜ます」等）が3文以上連続した場合にのみ行う。リズムを整える場合でも、文書の立場に合致した文末の種類（勧め・決まり・説明）は変えずに維持する。AIっぽさのない自然な文は、文末だけを変更しない。直す箇所がほとんどない場合は無理に書き換えない。

### 原則 9: ダッシュ記号（em dash）の排除

逆瀬川 (2026) および Czuma (2026) が報告している通り、AI生成文ではダッシュ記号（「—」「―」）が過剰に出現する傾向がみられる。これは英語の思考様式やMarkdownの癖が漏れ出した結果である。日本語の自然な接続助詞や句読点に置き換える。ダッシュを外して前後を1文につなぐとき、前にある理由や条件（「〜ため」「〜なら」など）がつないだ後ろの部分までかかるようになるなら、2文に分ける。

| 不自然な例（ダッシュ挿入） | 自然な表現 |
|---|---|
| 重要な機能――とりわけ認証周り――は慎重に実装する必要があります。 | 認証機能をはじめとする重要な処理は、慎重に実装する必要があります。 |

### 原則 10: 不要な補足カッコ（）の排除

情報量が増えない言い換えや同義語の補足カッコを全廃する。

| 不自然な例（重複カッコ） | 自然な表現 |
|---|---|
| 修正前のAI生成文（素の出力） | 修正前のAI生成文 |
| 不自然な日本語（いわゆるAI臭さ） | AI特有の不自然な日本語 |

必要な情報は地の文に直接組み込み、意味の重複する注釈カッコを削る方針をとる。

### 原則 11: 和欧文間の不自然な半角空白の排除

英語の単語区切り感覚を引きずり、英単語やアルファベットの前後に不要な半角空白を空けるクセを禁止する。日本語の助詞や平仮名とアルファベットの間は空白を空けず自然に接続させる。Markdown の太字の印の外側に、表示のために入れる半角スペースは例外とする（原則 14）。

| 不自然な例（不要な空白） | 自然な表現 |
|---|---|
| `この README は、 yomiyasu で 生成させた文章です。` | このREADMEは、yomiyasuで生成させた文章です。 |

### 原則 12: 絵文字および文末の装飾としてのコロン（：）の排除

Zhang et al. (ACL 2025) のフォーマットバイアス研究に基づき、装飾記号を完全に排除する。見出し、箇条書き、本文、テーブル内を問わず、絵文字は一切使用しない。また、箇条書きの前置き文や見出し直後、文末に全角コロン（：）を配置しない。句点（。）で文を閉じるか、不要な前置きを省略して直接記述する。
ただし、ラベルと値を対応づけるコロンは装飾ではない。「日時：10時」「対象：社内ポータル」のような元の区切りは残す。URLやコード内のコロンも変更しない。コロンを新たに足したり、前置きの不要な文末コロンまで残したりする規則ではない。

### 原則 13: 段落と文の論理構造の整流（つながりと話題の整理）

AI文章は、文と文をつなぐ接続詞が前後の論理と合っていなかったり、中身のない予告文で文字数を稼いだり、1つの段落に無関係な話題が混ざったりしやすい。これらを整理し、論理の流れを一読で理解できるように整える。

1. **つなぎ言葉・指示語の接続先検証**: 「ただし」「しかし」「また」「そのため」などの接続詞、主題の「も」、文頭の指示語（これ、それ、こうした等）は、前後の文と何をつないでいるかを確かめる。前後関係から正しい接続が明らかな場合は適切な言葉に直し、判断できない場合は無理に直さず書き手に確認する。
2. **予告だけの文の解消**: 中身を言わずに予告だけを行う文（「ここで重要なポイントがあります」「理由は以下の通りです」等）は、予告の重み（重要など）を述語に残しながら、続く中身の文と1文にまとめる。まとめることで意味が変わる場合は残す。
3. **1段落1話題**: 1つの段落には1つの話題だけを置く。話題の異なる段落同士を安易にまとめない。1つの段落に複数の話題が混在している場合は、文の順序を変えずに適切に分割する。
4. **主述のかみ合わせ**: 主語と述語がねじれている文は、元の文の意図が通じる範囲で正しく対応させる。
5. **修飾と条件の掛かり先**: 修飾語がどの語に掛かるか、条件・例外・否定・限定・数量がどの動作や判断に掛かるかを確かめる。
6. **並列と名詞の連続**: 並列した項目が共通する述語につながるか、名詞や長い節によって動作や判断の関係を追いにくくなっていないかを確かめる。
7. **操作と結果の対応**: 複数の操作の注意事項では、各操作とその結果を区別できるか確かめる。追いにくい場合は必要な用語を残して文や行を分ける。結果を表す語の意味が確定しない場合は、推測で具体化せず書き手へ確認する。

読み違い、または関係を追う負担を具体的に特定できた箇所だけで、修飾語の移動、名詞を動作として書くこと、接続・読点の整理、分割を検討する。変更は問題箇所の近くに絞る。語順を変えたり文を切ったりつないだりした後も、主張・比重・言い切りの強さ・文の働きと、条件・否定・並列・時系列の関係を確かめる。文末は原則2、分割は原則7、太字は原則14の方針を維持する。

複数の読みが残り、原文と提供文脈から関係を確定できない場合は、その関係を勝手に決めて直さない。確認が必要な箇所を「書き手に確かめたい点」へ出す。補う語にも原文や前後の根拠が必要である。元から自然で関係が追える箇所は残す。
接続や主述を直す箇所では、内部メモで「結論(比較, 方針)」「順序(A, B)」「条件(C, 動作)」、述語ごとの主体・対象、使役の相手を対応づける。原文にない因果や項は「?」とし、勝手に埋めない。修正後も同じ関係を追えるか確かめる。記号化は点検の補助であり、意味の等価性の証明や新しい出力欄にはしない。

| 確認する表現 | 整理または保持する表現 | 解説 |
|---|---|---|
| 開発を円滑に進める上で、意識したい点があります。定期的な進捗共有を行うことが推奨されます。 | 開発を円滑に進める上で意識したい点として、定期的な進捗共有を行うことが推奨されます。 | 予告を統合しても、意識したいという重みと、推奨されているという働きを残す。効用の断定へ変えない。 |
| エラー処理を組み込みました。また、通信失敗時にも自動で再試行が行われます。 | エラー処理を組み込みました。また、通信失敗時にも自動で再試行が行われます。 | 実装済みという事実と、処理の動作説明を区別して残す。再試行も今回実装したとは決めない。 |
| 設定を変更しました。ただし、再起動が必要です。 | 設定を変更しました。ただし、再起動が必要です。 | 変更済みという完了事実と、再起動が必要という留保を残す。「ただし」を不要と決めない。 |

以下は構造の点検用に作成した例である。修正案は、記載した文脈がある場合に限って検討する。

| 原文と提供文脈 | 検討する文 | 保持する関係 |
|---|---|---|
| 処理の実行の完了の確認後に通知を送る。 | 処理の実行が完了したことを確認してから、通知を送る。 | 完了を確認した後に通知する順序。担当者や期限は足さない。 |
| 私は昨日、届いた荷物を開けた。文脈では開けた日が昨日で、到着日は未指定。 | 私は届いた荷物を昨日開けた。 | 昨日は開封日に掛かる。主語と常体は保つ。荷物が届いた日や、今日開けたという情報は足さない。 |
| 通信が切れた場合だけ、再送します。 | 通信が切れた場合だけ、再送します。 | 再送の限定が明確なので残す。「だけ」を落とさない。 |
| 全員が賛成したわけではありません。 | 全員が賛成したわけではありません。 | 全員賛成の否定。全員反対や賛成者の有無を確定しない。 |
| 形式が正しければ取り込み、違っていれば処理を中止して通知します。 | 形式が正しければ取り込み、違っていれば処理を中止して通知します。 | 二つの分岐が追えるので残す。正しい形式の場合にも中止や通知を適用する文へ変えない。 |

### 原則 14: Markdown の太字が表示される書き方

Markdown として表示される文章（GitHub、技術記事など）で太字を残すときは、太字として正しく表示される書き方にする。
GitHub Flavored Markdown や CommonMark では、`**` のすぐ内側が記号（「」『』（）【】、。やバッククォート等）で、すぐ外側が文字（ひらがな・漢字・英数字）である場合、構文規則上太字として解釈されず、`**` がそのまま文字として表示されてしまう。
この仕様は、CommonMark Spec 0.31.2（2024-01-28）の 6.2節「Emphasis and strong emphasis」における left-flanking / right-flanking delimiter run の定義、および GitHub Flavored Markdown Spec 0.29-gfm（2019-04-06）に基づく。
ただし、記号として扱われる範囲には仕様の版によって違いがある。公開されている [GitHub Flavored Markdown Spec 0.29-gfm](https://github.github.com/gfm/#punctuation-character) では ASCII の句読記号と Unicode の P 類（句読点類: Pc、Pd、Pe、Pf、Pi、Po、Ps）を記号として数えるのに対し、[CommonMark Spec 0.31.2](https://spec.commonmark.org/0.31.2/#unicode-punctuation-character) ではさらに Unicode の S 類（記号類）も記号として数える。したがって、矢印「→」などの非 ASCII の S 類に接する太字が、GitHub でも必ず同じ理由で崩れるとは限らない。
現在の yomiyasu のスクリプトは、GFM と CommonMark の両方で表示される形を検査している。この保守的な方針や、かっこの内側・句点を外・最後に空白という直し方の順は変えない。なお、CommonMark のフォーラムの「Emphasis and East Asian text」（2017年6月）でも、日本語の `猫は**「のどか」**という。` で太字にならない例が挙げられている。

太字を残すときは、次の優先順で直す。
1. かっこごと太字にしているときは、かっこの内側だけを太字にする。
2. 太字の終わりが句点などのときは、句点を太字の外に出す。
3. 1と2ができないとき（コードで始まる・終わる太字、かっこが2つ以上ある太字など）は、`**` の外側の、文字に接する側に半角スペースを1つ入れる。この半角スペースは表示のためのものであり、和欧文間の不自然な半角空白には当たらないため消さない。

元の文で太字にならない書き方になっている箇所は、太字を残すなら、ほかに直す箇所がない文でも同様に直す。意味は変わらないため「変えたところ」には書かない。なお、太字を増やす規則ではなく、太字を減らす規則（domains/tech.md 等）はそのまま維持する。

| 表示されない書き方 | 表示される書き方 | 直し方 |
|---|---|---|
| `次に**「文書の立場」**を決めます。` | `次に「**文書の立場**」を決めます。` | かっこの内側だけを太字にする |
| `これは**必須です。**詳しくは下に書きます。` | `これは**必須です**。詳しくは下に書きます。` | 句点を太字の外に出す |
| `立場は**「勧め」か「決まり」**で決めます。` | `立場は **「勧め」か「決まり」** で決めます。` | `**` の外側の文字に接する側に半角スペースを1つ入れる |
