# 自然な日本語への構文変換原則

この文書は、AI生成文で見直したい構文と、意味を保ちながら自然な日本語に整える指針をまとめている。SKILL.md の手順3で、主述、修飾、つながり、文の分け方、見出し、コピー調、記号と太字の扱いに迷ったときに、該当する原則を読む。どの原則も、SKILL.md 4.1（意味を保つ）と4.2（足さない）の範囲で使う。

文長や装飾の上限などの数値は、本スキルの編集の目安である。参考にした研究と調査は README の「謝辞・参考文献」にまとめている。

---

## 文章を整える原則

### 原則 1: 動作主・対象・動作の明確化

言い換える前に、主語と述語、修飾語と掛かる先、指示語と指す対象を確かめる。原文から確定した関係を読み手が追えるように整理し、未確定の関係は確定させない。省略や受動態そのものを不自然とはみなさず、文脈から関係が伝わる箇所は残す。ただし、コピー調の本文や見出しは、原則16に従い、意味と役割を保って整える。

単語の言い換えにとどめず、「誰が・何を・どうした」を読み手が追えるようにする。動作主（S）は、元の文や前後から処理や判断を行う主体が分かる場合だけ、必要な位置で明記する。分からない動作主や、元にない担当者は作らず、自然なシステム動作まで人間の行為へ変えない。省かれた目的語や対象を補うのは、原文・依頼・提供資料に対象と関係が明示されているときだけに限定する。推測で創作したり、近くにある名詞というだけで対象を選んだりはしない。「これ」「片方」が指す対象（O）も、文脈から分かる場合だけ具体的な名詞に置き換える。何を指すか追う必要がある名詞は、「もの」などへ不用意にぼかさない。動詞（V）が抽象的で伝わりにくい場合は、文脈に合う平易な言葉に直す。補った語があれば、「変えたところ」に書く。
複数の述語で動作主が変わる文は、述語ごとに「動作(主体, 対象)」を確かめ、原文や提供文脈で分かる動作主が切り替わる箇所は、その主体を明記する。例えば「上長が差し戻した場合、システムが通知します」と書き、差し戻す人と通知する主体を区別する。使役は「誰が・何に・何をさせるか」を区別し、助詞や使役を変えたときも対応を確かめる。長い節を読み戻らないと対象を追えない場合は、対象の再掲や節の分割を検討する。不明な主体や対象は作らない。
元から「もの」「それら」で処理や選別の対象を省いている場合も、対象が確定し、前の文から拾い直す負担があるなら、原文の名詞を再掲する。名詞が近くにあることだけで対象を選ばず、複数候補を一つへ狭めない。確定した対象の再掲と、新しい対象を足すことを区別する。
語が既出でも、語どうしの関係が同じとは限らない。助詞・修飾の位置・述語を変えるときは、対象と扱い、実行と待機の主体、修飾先を原文と照らし合わせる。「XをYとして登録」と「XのYを登録」のように、使う語が同じでも対象が変わる場合がある。同じ関係と確定できなければ原文を保ち、書き手に確認する。原文が複数の読みを許す場合は、自然に言い換えるためだけに一つの読みへ決めない。
原文と改稿の両方で、述語を中心に語句を分け、主語・対象・扱い、修飾語→係る先、指示語→指す対象を短く対応づける。名詞句の修飾を担当者の動作へ移す場合は、意味が同じと確認できる根拠が要る。「独立した展示」を「独立して担当する」へ変えると、展示の性質が担当者の行為へ移る。文書の話題だけで修飾先を確定せず、複数の読みが残れば原文を保って確認へ出す。語形を変えても意味が保てる場合は整理してよいが、矢印が引けること自体を等価性の証明にはしない。
主述や使役の対応を直すときは、まず原文の動詞を保って、確定した主語・相手・対象を明記する案を検討する。動詞自体を直す理由がないのに、対象を補えば伝わる文を別の長い構文へ組み替えない。比喩など動詞を直す理由がある場合も、元の動作と関係を保つ。動作を名詞にして「〜を行う」と書くより、対象と動詞を直接つなぐ方が自然な箇所は、「値を代入する」「変更内容を共有する」のように書く。何を扱うかが分かる対象を落としたり、動作を別の動作へ変えたりしない。失敗時に値を代入しない処理を「falseを代入する」と変えるような、実際の条件や動作の改変は避ける。
「〜することができる」のように「こと」を含む外枠が重なって読みにくい箇所は、意味を保てる範囲で動詞へ戻す。外枠を外しても義務・決定・経験・可能・頻度・評価の意味は保ち、内容を指す名詞節は残して、「こと」の数だけで削らない。「〜かを確かめることが重要」のような評価の文は、「こと」を減らす目的で指示へ変えない。まだ確かめていない成否は「〜かを確かめる」と書けるが、「一致していることを確認した」のような確認済みの結果は問いへ変えず、「言われたこと」も言われたかどうかの問いにしない。削除などの後続操作を行う条件は、後ろの文にある「〜でない場合」「不明な場合」などの扱いまで含めて読み、落とさない。原文と改稿で、確認の対象・結果・操作の条件が同じかを確かめる。
動詞を平易に言い換えた後も、文全体の語順を確かめる。仕事の通知を表す「連絡が担当者に飛ぶ」を直す場合、「担当者に連絡が届く」のように、受け手を先に置き、主語と述語を追いやすくする案も検討する。主述を近づけるために修飾先や条件の範囲を変えず、元から自然で関係が追える語順は残す。

| 確認する表現 | 整理した表現 | 解説 |
|---|---|---|
| 両者を突き合わせることで、差分が浮き彫りになる。 | 両者を比べると、違いがはっきり分かる。 | 元にない名詞を足さず、「浮き彫りになる」の含みを「はっきり分かる」に残す。常体も保つ。 |
| 処理を流すたびに、状態が勝手に書き換わっていく。 | 処理を流すたびに、意図せず状態が書き換わっていく。 | 「勝手に」の不本意な含みを「意図せず」に残す。「流す」の指す処理は文脈なしに限定しない。 |
| 使い倒すことで、道具が手に馴染む。 | 徹底して使い込むことで、道具を思い通りに扱えるようになる。 | 「使い倒す」と「手に馴染む」の含みを平易な言葉で残し、常体も保つ。 |
| 前後を取り違えると、意図しない挙動につながる。 | 前後の順序を間違えると、意図しない動き方につながる。 | 「挙動」を平易にし、原因と結果の関係、常体を保つ。 |

### 原則 3: 道具や概念を擬人化した表現の整理

道具や概念に感情や意志を持たせている表現（「コードが語る」「システムが願う」等）を直す。道具や仕組みの働きを客観的に述べている文（「このツールは通信ログを収集します」等）はそのまま残す。感情や意志を持たせていなくても、人が自分でした行動や判断を、抽象名詞が作用したように書いている文（「見積もりの甘さが判断を遅らせた」等）は、原文や前後から誰の行動か分かる場合だけ、その人の行動として書く。
直す場合も、元にない条件（「〜を使えば」）や可能（「〜できます」）を勝手に足さず、客観的な事実として記述する。

| 確認する表現 | 整理または保持する表現 | 解説 |
|---|---|---|
| このドキュメントが、APIの仕様を語っている。 | このドキュメントにAPIの仕様が書かれている。 | 内容の所在として書き直し、常体を保つ。 |
| 新しいガイドラインが、チームに変化を促す。 | 新しいガイドラインがチームに変化を促す。 | 作用の説明として保持する。実際に変化が進んでいるという出来事へ変えない。 |
| コードが自らの振る舞いを証明する。 | コードが自らの振る舞いを証明する。 | 「証明」が何を指すかを文脈で確かめる。非生物主語だけを理由に「示す」へ弱めない。 |
| 画面の配置が、利用者の迷いを誘う。 | 画面の配置が利用者の迷いを誘う。 | 原因と結果の説明として保持する。配置が分かりにくいという評価や、状況が変化したという情報を足さない。 |
| 確認作業の見積もりの甘さが、提出の判断を後ろ倒しにした。（※書き手自身の遅れの報告） | 確認作業の見積もりが甘く、提出を決めるのが遅れた。 | 道具や物の作用ではなく、書き手が自分でした見積もりと判断を、抽象名詞の作用として書いている。原因（見積もりの甘さ）と、遅れたのが提出の判断であることを残し、書き手の行動として書く。原文にない別の原因や出来事には変えない。常体も保つ。 |

### 原則 4: 比喩動詞の具体化とふだん使う言葉への変更

「倒す」「効く」「溶かす」「潰す」といった比喩が不自然な場合は、文脈に合うふだんの言葉に直す。不必要に難しい技術用語や硬い漢語へ置き換えず、「発生」「担保」など硬い2字漢語を不要な場面で連発しない。専門的な意味で使う語は、slop-catalog.md 2章に従い、定着した用語と名称の対応を保つ。意味を保った自然な言い換えができない場合は無理に変えず、元の動詞を残す。語ごとの言い換えの候補は slop-catalog.md 1章にある。
比喩や言い回しが持っていた「含み（気持ちや評価の向き）」は必ず残す。
- 含みの例: 「うっかり」の不注意、「ようやく」の待ちくたびれた感じ、「〜てしまった」の後悔、「地味に」の目立たないけれど確かにある感じ。
- 比喩の語は言い換えてかまわないが、その語が伝えていた含みや理由は、別のふだんの言葉で補って言い表す。
- 言い換えるときは、「良いほうに働いている」「助けになっている」「じわじわ助けになる」のように、効き目や評価だけをぼんやり述べる言い方にしない。何がどう変わったのかを書く（おかげで少しずつ変わってきている）か、ふだんの文章で使われる言い方（少しずつ薬になっている）を選ぶ。「じわじわ効いている」のように元の比喩を残すこともしない。
- 比喩動詞だけでなく、副詞や前置きの言い回しも同じ扱いとする。

データやシステムに対する「壊れる」は、「おかしくなる」「使えなくなる」のように、意味の広さが同じふだんの言葉に改める。「データの整合性が失われる」「不整合が生じる」と書くのは、元の文や前後から整合性の話だと明らかなときだけに限定し、言い切りの強さも保つ。時計や機械、身体（お腹を壊す等）の文字どおりの「壊れる」はそのまま残す。
「静かに」「黙って」は、「気づかないうちに」「知らないうちに」のように気づけないという幅を保つ。「エラーを出さずに」「通知なく」と書くのは、元の文や前後から、エラーや通知が出ないことがはっきり分かるときだけにする。

「骨が折れる」「手を焼く」「目から鱗が落ちる」「首を長くして待つ」のような、ふだんの日本語で定着した慣用句は、AIっぽい比喩として扱わず、そのまま残す。業務仕様でも、意味を取り違えるおそれがなければ残す。迷ったときの目安は、その言い方を、AIが広まる前の人の文章でもふつうに見かけるかどうか。見かけるなら残す。

| 比喩表現 | 自然で直接的な表現への置き換え | 解説 |
|---|---|---|
| 例外が起きたときは、安全側に倒す。 | 例外が起きたときは、安全を優先する。 | 「倒す」を平易にし、元にない処理内容は補わない。常体も保つ。 |
| この工夫が、後々の運用で地味に効いてくる。 | この工夫が後々の運用で目立たないながらも役立ってくる。 | 「地味に」の含みと、後々役立つようになることを残す。条件や余計な強調語は足さない。 |
| 古いコードの問題を1つずつ潰していく。 | 古いコードの問題を1つずつ直していく。 | 「潰す」を平易な動詞に直し、常体も保つ。 |
| 通信が切れた瞬間に、画面が静かに固まる。 | 通信が切れた瞬間に、気づかないうちに画面が動かなくなる。 | 「静かに」を気づけない幅のまま直し、出来事のタイミングと常体も保つ。 |
| 設定の反映に丸一日溶かしてしまった。 | 設定の反映に丸一日かかってしまった。 | 後悔の含みと常体を残して平易に記述する。 |

### 原則 5: 不要な前置きと否定対比の整理

AIは「重要なのは」「結論から言うと」といった不要な前置き（セルフラベリング）や、否定対比の構文を好む傾向がある。
前置きを削ってよいのは、削っても主張が変わらないときだけである。「重要なのは」「大事なのは」が「何が大事か」という評価を担っているときは、評価を消さずに述語に残す（「〜が大事です」「〜が重要です」）。
理由・対比・結論や、説明から方針への切替を担う前置きも保護する。比較結果を採用方針へつなぐ「結論として」などは、他の語から同じ関係が読めなければ削らない。「一般に〜」「現代社会において〜」「もちろん〜とは限らないが」などが意味を担わない前置きなら削る。語の一覧は slop-catalog.md 6章にある。
文頭の「もちろん、」のあとに数語だけが続いて終わる短い文（「もちろん、失敗もする。」）で、読み手が思いそうなことを先回りして認めているものは、AIの文章らしく見えやすいため、随筆でも「もちろん、」を外す。当然のこととして認める含みがあることだけを理由に残さず、その含みを「当然、」「言うまでもなく、」などの別の語で補うこともしない。認めている内容とその程度は残し、元にない理由や因果やつなぎの語は足さない。会話や引用の中の「もちろん」、問いや依頼への答え（「もちろんです。」）、条件や前提を確かめる文、「もちろん、」の後に同じ文の中で具体的な内容が続く文、文の途中の「もちろん」（「AはもちろんB」など）は、この扱いの対象にしない。
否定対比（AではなくB）は、Aを消した文で主張が変わらないときだけ肯定文にする（確かめ方と残す例は rephrase-test.md 3章）。Aだと思われがちなところをBだと言い直しているような、意味や比重を担っている否定は、否定を残したまま言い回しだけを自然にする。否定していたAを「Aに加えてB」と並べたり、「AよりB」と順位づけしたりしない。否定を残すときに、元にない理由の文や勝手な強調語（「そのもの」等）は足さない。否定のあとに「でもある」と続ける文は、否定と「も」を保って一つの文のまま残し、2文に分けたり、その意味を書き手に尋ねたりしない。「弱みであると同時に、視点の違いでもある」のように、否定していたAを認める形にも変えない。
直前で問いなどとして挙げた二つを、続く文が「〜ではない」「〜でもない」のような否定の形で両方とも打ち消すだけの場合は、「どちら」が何と何を指すかが直前の文脈から一通りに決まるときに限り、挙げた語を繰り返さずに「どちらでもない。」（敬体なら「どちらでもありません。」）と短く受けてよい。「どちら」が直前の二つを指すので、打ち消す内容は保たれる。打ち消すほかに問いにない内容（「決して」のような強めの語、限定、なぜ違うかの説明など）を含む否定は、短くせずに書く。

| 確認する例（前置き・対比） | 整理または保持する表現 | 解説 |
|---|---|---|
| 結論から言うと、このボタンを押すだけで完了します。 | このボタンを押すだけで完了します。 | 単なる前置きは削り、本題から直接書く。 |
| 重要なのは、画面の見た目ではなく裏側のデータ構造です。 | 画面の見た目ではなく、裏側のデータ構造が重要です。 | 評価（重要）を述語に残し、否定対比を保つ（「そのもの」等は足さない）。 |
| 目的は、機能の追加ではなく使いやすさの向上です。 | 機能の追加ではなく、使いやすさを高めることが目的です。 | 否定対比が方針の切り替えを示しているため、否定を残して表現を整える。 |
| 雑談は仕事の妨げではなく、相談のきっかけでもある。 | 雑談は仕事の妨げではなく、相談のきっかけでもある。 | 直さずに残す例。否定のあとに「でもある」と続ける文は、否定と「も」をどちらも保ち、一つの文のまま残す。「仕事の妨げではない。相談のきっかけでもある。」と2文に分けたり、「妨げであると同時に」のように否定した内容を認める形にしたりしない。「でもある」の意味を書き手に尋ねることもしない。常体も保つ。 |
| これは努力ではない。才能でもない。仕組みだ。 | これは仕組みだ。 | 二度否定してから三度目に言い切る型。前後に努力や才能だとする見方が出てこず、否定が言い切りを強めるだけの修辞なら、言い切りの文だけを残す。読み手が努力や才能によるものと考えがちな文脈なら、三つの文を一つにまとめ、否定を残して「これは努力や才能ではなく、仕組みだ。」とする。ただし、直前の文が「努力か、才能か」のように二つを挙げて問い、否定がその二つを打ち消すだけで、「どちら」が何と何を指すかが直前の文から一通りに決まる場合は、問いの語を繰り返してまとめなくても、「これはどちらでもない。仕組みだ。」と短く受けてよい。どの場合か決められなければ原文を残す。常体も保つ。 |

### 原則 6: 意味の保持と文の種類（例）

意味を保つ規則（主張、比重、言い切りの強さ、文の働き）と、足さない規則は SKILL.md 4.1・4.2 にある。提供された定義や値と状態の対応を説明に活かす決まり（SKILL.md 4.2）は、読み手に不要な説明を毎回足す決まりではない。パラメータ、バージョン要件、例外条件などの技術的な制約や前提も削らない。言い切りの強さは、「おそれがあります」と弱めたり、「〜と言えるでしょう」を断定に上げたりしない。評価や性質の文（「〜が大事」「〜の本質は」）を、目標や予定の文（「〜を目的とする」「〜を高める」）に変えない。
話の中身と、その話がどういう種類の話か（事実か、例えか、冗談か）は分けて確かめる。SKILL.md 4.1 の7つの文の種類で各文を記録し、書き直したあとも同じ種類に保つ。種類ごとに、しない書き換えの例を挙げる。

| 文の種類 | 元の文 | しない書き換え |
|---|---|---|
| 事実 | 障害は10時に復旧した。 | 障害は10時に復旧したようだ。（推量を足して事実をぼかす） |
| 意見・評価 | この画面は分かりにくいと思う。 | この画面は分かりにくい。（意見を事実として言い切る） |
| 依頼・決まり | 申請は金曜までに出してください。 | 申請は金曜までに出します。（依頼を説明や予定にする） |
| 例え・比喩 | 机の上はまるで戦場のようだ。 | 机の上は戦場だ。（例えに使った物を事実のように言い切る） |
| 皮肉・冗談・反語 | こんな手順で、誰が迷わずに使えるだろうか。 | 誰が迷わずに使えるかは分からない。（反語をただの疑問にする） |
| 仮定・予測 | 予算が通れば、来月から始められる。 | 来月から始める。（条件と見込みを外して予定にする） |
| 引用・伝聞 | 原因は設定の誤りだとされる。 | 原因は設定の誤りだ。（伝聞を断定にする） |

例えの文は、例えのまま残すのが基本である。比喩動詞の具体化などで例えの語を外すときも、例えが伝えていた中身を元と同じ強さで書き、比喩をほどいた説明にしない。皮肉や反語は、本文の文脈から確定できる場合だけ扱い、決めきれなければ原文を残す。
情報が足りず確定した本文を書けないときの書き方は、`references/output-format.md` 6章にある。

### 原則 7: 文長・読点・漢語の連続の調整

平均文長30〜45文字は、本スキルの編集の目安であり、論文中の実験数値ではない。この長さは文章全体の平均の目安で、一つひとつの文をこの範囲にそろえるために分けたりつないだりはしない。60文字を超える複文は分割を検討する目安とするが、長さだけを理由に分けない。
長い文を分けるのは、手段・理由・順序・対比などのつながりを、後ろの文のつなぎ言葉（「そのため」「こうすることで」「一方で」「反対に」など）で残せるときだけに限定する。目的や理由が文末の結論に掛かる文は、分けると「何のために何が必要か」の向きが変わりやすいため分けない。「設定を先に読み込んで、起動を速くするために使います」のような、〜するために〜です／〜しますの形も同じように扱う。分けると向きが変わるなら原文を残す。
10文字未満の短文を続けて、必要以上に細切れの文章にしない。「ます。」で短い文に区切りすぎない。原文に「効く。重い。安い。」のような評価の語だけの短文を並べる型がある場合は、原則16に従う。
読点は1文あたり0〜2個を目安にし、不自然な位置や掛かり先を読みにくくする箇所を調整する。元から読みやすい文の読点は、数や見た目だけで削らない。短い主題句から述語まで続けて読め、読み分けの役割がない読点は、元の文にあっても外す。「操作画面の『旗』はまだオンにしません」のように書き、実際の項目名は保つ。文頭で間を作るだけの読点（「前提を、〜」「ここでは、〜」など）や、主題のすぐあとに間を作るだけの読点（「応答は、〜」）も足さない。条件・逆接や長い句を読み分ける読点は残す。「会議では、担当者が説明しました」のように、主題とその後の動作主を読み分ける読点は、句が短くても残す。
読点の整理だけを理由に、元から読みやすい文の語順や述語を組み替えない。読点だけを整えるときは、原文の動作主・対象・述語を残す。誰かが操作を行わないという記述を、対象の状態が変わらないという保証へ変えない。
進捗報告で別々の作業の完了・未完了を伝える場合は、状態ごとに文を分けて書く。逆接や留保そのものが結論の解釈を左右する文は、その関係を残す。
漢語が続いて硬くなった箇所は、文脈に合うふだんの言葉や動詞に直す。
独立した変更点、手順、担当と結果の対応など、並列関係が明確で読みやすい箇条書きは、AI調に見えるという印象や比率の数値だけで無理に地の文へ戻さず維持する。地の文にすると同じ文末が単調に続く場合も、箇条書きのまま残す。論理関係を分断しているなど具体的な理由がある場合に地の文へまとめる。地の文にするときも、各項目の働きと、変更指定のない常体・敬体を保ち、元にない評価や義務（〜が大切です、〜する必要があります等）を足さない。語尾の扱いは stance-and-endings.md 9章に従う。単に並んでいるだけの項目は、箇条書きのまま残してよい。

### 原則 8: 文末のリズムと文の働きの保持
滑らかに読めることだけで、意味や文の働きが保たれているとは判断しない。
文末のリズム調整は、AIっぽさを直すついでに単調な繰り返しが生じて読みにくい場合に行う。同じ意味の変更動詞が隣り合う場合も語順やまとめ方を工夫するが、語尾を散らす目的で文の働きや時制を変えない。リズムを整える場合でも、文書の立場に合致した文末の種類（勧め・決まり・説明）は変えずに維持する。AIっぽさのない自然な文は、文末だけを変更しない。直す箇所がほとんどない場合は無理に書き換えない。同じ文末が続くことは、読みにくさを見直すきっかけにとどめ、AIの文の目印とはみなさない。
語尾を散らすために述語を落としたり、目的語の後に間を置く読点を足してコピー調にしたりしない。コピー調の本文・見出し・自分で書く変更説明の扱いは、原則16に従う。原文の引用は改変しない。

### 原則 9: ダッシュ記号（em dash）の排除

逆瀬川（2026）やCzuma（2026）のダッシュ記号に関する調査を参考に、本スキルでは下の表の記号（em dash などの長い横線と、罫線文字の横線）を、日本語の自然な接続助詞や句読点に置き換える。罫線だけの区切り線や、木構造・図の罫線、引用の出典を示す記号は、文中の装飾ではないので残す。引用や、小説・随筆で書き手が文体として使っているダッシュ（会話や言いさし、間、言い換えなど）は昔からある書き方なので残す。ただし、技術記事、業務文書、説明文のダッシュと、補足や言い換えを毎回同じようにダッシュで挟んでいる箇所は置き換える。小説やエッセイでも、補足や言い換えを毎回同じ形でダッシュで挟み、その数が多い場合は見直す。名詞を並べて末尾をダッシュで閉じ、余韻を持たせる書き方は、並べた語が何についての列挙かを述語で言い切る。文脈から述語が分からない場合は推測で補わず、記号だけ外して「速さ、軽さ、静けさ。」のように並びを残し、書き手に確認する。ダッシュを外して前後を1文につなぐとき、前の理由や条件（「〜ため」「〜なら」など）が後ろの部分まで掛かるようになるなら、2文に分ける。

| 置き換える記号 | 種類 |
|---|---|
| — ― | em dash などの長い横線 |
| ─ ━ ── | 文中に使われた罫線文字の横線 |

| 不自然な例（ダッシュ挿入） | 自然な表現 |
|---|---|
| 重要な機能――とりわけ認証周り――は慎重に実装する必要があります。 | 重要な機能、特に認証周りは、慎重に実装する必要があります。 |
| 新しいエディタで目指したのは、速さ、軽さ、静けさ──。 | 新しいエディタでは、速さと軽さ、静けさを目指しました。 |

### 原則 10: 不要な補足カッコ（）の排除

同じ意味を繰り返すだけの補足カッコを削る。

| 不自然な例（重複カッコ） | 自然な表現 |
|---|---|
| 修正前のAI生成文（素の出力） | 修正前のAI生成文 |
| 不自然な日本語（いわゆるAI臭さ） | AI特有の不自然な日本語 |

必要な情報は地の文に直接組み込み、同じ意味を繰り返す注釈カッコを削る。

強調のためだけのカギ括弧も見直す。「『速さ』と『軽さ』を『両立』させた『新しい』ツール」のように、短い語を次々とカギ括弧で括っている場合は、外しても意味が変わらないものだけ外す。引用、発話、作品名、初出の用語の定義、画面の項目名（「保存」ボタンなど）、皮肉や「いわゆる」の含みを担うカギ括弧は残す。どの働きか決められないものも残す。

### 原則 11: 和欧文間や数値の空白の扱い

英単語やアルファベットの前後に空白があることだけを理由に、一律に空白を削ったり、逆に一律に空白を入れたりしない。原文の書式や、依頼で指定されたスタイルを保つ。数値の前後の空白も同じ理由で詰めない。
ただし、太字の表示に必要な空白や、太字の内側にある不要な空白を直す作業は、英単語前後の削除とは別に維持する（原則14）。コマンド・コード・URLに含まれる必要な空白も勝手に消さない。

### 原則 12: 絵文字および文末の装飾としてのコロン（：）の排除

本スキルでは、見出し・箇条書き・本文・表を問わず絵文字を使わない。箇条書きの前置き文や見出しの直後、文末に装飾としての全角コロン（：）も置かない。句点（。）で文を閉じるか、不要な前置きを省いて直接書く。紹介記事・宣伝文で書き手が気持ちや勢いを表すために使った絵文字は、外さずに残す（doc-types/promo.md）。
ただし、ラベルと値を対応づけるコロンは装飾ではない。「日時：10時」「対象：社内ポータル」のような元の区切りは残す。URLやコード内のコロンも変更しない。コロンを新たに足したり、前置きの不要な文末コロンまで残したりする規則ではない。
ラベルと値の区切りかどうかは、値の中身で見分ける。値が日時、場所、担当、数値のような短い事実なら、区切りとして残す。`- **特徴**: 高速に動きます` のように、抽象的な語を太字のラベルにしてコロンでつなぎ、値が一文の説明になっている箇条書きの項目が続く場合は、太字とコロンを外してラベルの語を説明の文に含めるか、地の文にするかを検討する。どちらの場合も、ラベルが示していた項目の区別と、項目の数・順序は変えない。並列関係が明確で読みやすい箇条書きは、地の文にせず、原則7のとおり箇条書きのまま残す。決められなければ原文を残す。
原文が「■」「・」などの記号で見出しや項目を示している場合は、依頼で指定がなければ、Markdownの「##」や「- 」に置き換えず原文の記号を保つ。Slackやメールなどに貼る文章では、Markdownの見出しが記号のまま表示されることがある。

### 原則 13: 段落の話題と文のつながりの整理

文と文の接続が合わない箇所、中身のない予告文、1つの段落に無関係な話題が混ざった箇所を見直す。話題とつながりを読み手が追えるように整える。

1. **つなぎ言葉・指示語の接続先**: 「ただし」「しかし」「また」「そして」「つまり」「そのため」などの接続詞、主題の「も」、文頭の指示語（これ、それ、こうした等）は、前後の文と何をつないでいるかを確かめる。文ごとに、前の文とどのような関係にあるか（理由、例示、但し書き、言い換え、補足、まとめ等）も内部で確かめる。「自然に読めるか」という感覚だけで判断せず、論理的な接続先を特定する。前後関係から正しい接続が明らかな場合は適切な言葉に直して「変えたところ」に出し、判断できない場合は無理に直さず「書き手に確かめたい点」に出す。文や段落の頭ごとに「また、」「さらに、」「加えて、」「なお、」が続き、外しても前後の関係が変わらないものは外す。逆接、理由、条件、例外を示す接続は外さない。
2. **予告だけの文の解消**: 中身を言わずに予告だけを行う文（「ここで重要なポイントがあります」「理由は以下の通りです」等）は、予告の重み（重要など）を述語に残しながら、続く中身の文と1文にまとめ、まとめたら「変えたところ」に出す。まとめることで意味が変わる場合は残し、「残したAIっぽいところ」に出す。「重要なポイントは3つです」「以下の3つの観点から説明します」のような数の宣言も、宣言した数と続く項目の数が合っている場合に限り、同じ基準で続く中身の文と1文にまとめる。長い説明で項目数の予告が読み手の案内になっている場合は残す。数が合わない場合は、宣言の数も項目も変えずに「書き手に確かめたい点」に出す。宣言の数にそろえるために項目を足したり削ったりしない。
3. **1段落1話題**: 段落ごとに「何の話をしているか」を1行でつかむ。1つの段落には1つの話題だけを置く。話題の異なる段落同士を安易にまとめない。1つの段落に複数の話題が混在している場合は、文の順序を変えずに適切に分割する。
4. **主述のかみ合わせ**: 主語と述語がねじれている文は、元の文の意図が通じる範囲で正しく対応させる。
5. **修飾と条件の掛かり先**: 修飾語がどの語に掛かるか、条件・例外・否定・限定・数量がどの動作や判断に掛かるかを確かめる。対象の一部や比べる項目、期間などの限定が前後の文にあっても、その限定がない文へ持ち込まない。指示語や「同じ」、用語の定義などで同じ限定が掛かると原文・依頼・提供資料から確定できる場合は、その限定を補ってよい。
6. **並列と名詞の連続**: 並列した項目が共通する述語につながるか、名詞や長い節によって動作や判断の関係を追いにくくなっていないかを確かめる。
7. **操作と結果の対応**: 複数の操作の注意事項では、各操作とその結果を区別できるか確かめる。追いにくい場合は必要な用語を残して文や行を分ける。結果を表す語の意味が確定しない場合は、配置だけで解決したことにせず、推測で具体化せず書き手へ確認する。

説明文や論考では、見出し・問い・列挙の導入が何の関係を説明すると述べているかを、全文で一度確かめる。個々の文が読めても、前段と列挙の対応や、結びの指示先が分かるとは限らない。列挙の前に「そこで」などがある場合は、何への対応なのかも確かめる。明確な対応は読み手が追えるように整え、分からない対応は推測で書き足さず、output-format.md 6章に従って本文の主張を保ち、確認が必要なら「書き手に確かめたい点」で尋ねる。独立した報告や項目を無理につなげず、仕組みの詳細が省かれているだけで意味不明とは判断しない。

同じ段落で一つの問題を説明した後、その対策を述べる文でも同じ問題を長く言い直している場合は、「この問題を防げます」のように、明確な指示語で受ける。原文にある反復だけでなく、書き直しで新たに重複した説明も整理する。複数の問題や条件の切替で、どの対象かを追うために必要な再掲は保つ。言い直すだけの締めや「まとめ」の扱いは slop-catalog.md 6章「言い直しの締め」に従う。

改行は、話題や説明の段階が切り替わり、分けると読みやすくなる箇所で、意味のまとまりごとに使う。出来事、現在の状態、今後の予定のように、報告の説明段階が切り替わる箇所でも、分けると読みやすければ改行を使う。新たに本文の行を分けるときは改行1つを基本とし、読みやすさを理由に空行を一律に増やさない。時制が変わるたびに機械的に改行したり、常に三段構成にしたりせず、条件と結果、理由と結論、操作の順序を読み違える位置では分けない。元からある意図的な段落分けや、見出し・箇条書き・コードなどの書式上の区切りは保つ。Markdownの改行指定と通常の行分けを取り違えず、句点ごとに機械的に改行せず、元から自然な短い段落や改行は保つ。

読み違い、または関係を追う負担を具体的に特定できた箇所だけで、修飾語の移動、名詞を動作として書くこと、接続・読点の整理、分割を検討する。変更は問題箇所の近くに絞り、意味が動きやすい修正は「変えたところ」に出す。語順を変えたり文を切ったりつないだりした後も、主張・比重・言い切りの強さ・文の働きと、条件・否定・並列・時系列の関係を確かめる。筆者が見聞きした日時と出来事そのものが起きた日時は区別する。述語ごとに誰の動作や報告かを対応づけ、見聞きした日時を出来事の日時へ移したり、現在の報告や伝聞を過去の発言へ勝手に変えたりしない。引用や予定、日時が指定されていない出来事も、意味や時制を保って書き分ける。原文の各主張の動作主・述語・対象、時、条件、文の働きは本文で追えるように保つ。提供文脈にある別の事実（聞き取った経験など）を書いたことだけで元の主張を保ったとみなさず、既知の関係を別の観察・経験・予定へ置き換えて消さないようにする。文末は stance-and-endings.md、分割は原則7、太字は原則14の方針を維持する。

複数の読みが残り、原文と提供文脈から関係を確定できない場合は、その関係を勝手に決めて直さない。語の指す対象が曖昧でも、結びつく動作や関係が分かるなら、元にない仕組みを推測で書き足さず、元の条件付きの主張と言い切りの強さをそのまま本文に残す（例は slop-catalog.md 5章の「境界」）。本文や確認の問いでも、不明な語が何を指すかを推測で前提にせず、時点・責務・範囲・判断条件などの種類や役割を勝手に狭めて決めつけない。確認が必要な箇所は「書き手に確かめたい点」で自然に尋ねる。補う語にも原文・依頼・提供資料に対象と関係が明示されている明確な根拠が必要である。元から自然で関係が追える箇所は残す。
接続や主述を直す箇所では、内部メモで「結論(比較, 方針)」「順序(A, B)」「条件(C, 動作)」、述語ごとの主体・対象、使役の相手を対応づける。原文にない因果や項は「?」とし、勝手に埋めない。修正後も同じ関係を追えるか確かめる。記号化は抜けを見つける点検の補助であり、意味の等価性の証明や新しい出力欄にはしない。メモは出力に加えない。

| 確認する表現 | 整理または保持する表現 | 解説 |
|---|---|---|
| 開発を円滑に進める上で、意識したい点があります。定期的な進捗共有を行うことが推奨されます。 | 開発を円滑に進める上で意識したい点として、定期的に進捗を共有することが推奨されます。 | 予告を統合し、動作を直接書く。意識したいという重みと、推奨されているという働きを残し、効用の断定へ変えない。 |
| エラー処理を組み込みました。また、通信失敗時にも自動で再試行が行われます。 | エラー処理を組み込みました。また、通信失敗時にも自動で再試行が行われます。 | 実装済みという事実と、処理の動作説明を区別して残す。再試行も今回実装したとは決めない。 |
| 設定を変更しました。ただし、再起動が必要です。 | 設定を変更しました。ただし、再起動が必要です。 | 変更済みという完了事実と、再起動が必要という留保を残す。「ただし」を不要と決めない。 |

以下は構造の点検用に作成した例である。修正案は、記載した文脈がある場合に限って検討する。

| 原文と提供文脈 | 検討する文 | 保持する関係 |
|---|---|---|
| 処理の実行の完了の確認後に通知を送る。 | 処理の実行が完了したことを確認してから、通知を送る。 | 完了を確認した後に通知する順序。担当者や期限は足さない。 |
| 私は昨日、届いた荷物を開けた。文脈では開けた日が昨日で、到着日は未指定。 | 私は届いた荷物を昨日開けた。 | 昨日は開封日に掛かる。主語と常体は保つ。荷物が届いた日や、今日開けたという情報は足さない。 |
| 通信が切れた場合だけ、再送します。 | 通信が切れた場合だけ、再送します。 | 再送の限定が明確なので残す。「だけ」を落とさない。 |
| 全員が賛成したわけではありません。 | 全員が賛成したわけではありません。 | 全員賛成の否定。全員反対や賛成者の有無を確定しない。 |
| 形式が正しければ取り込み、違っていれば処理を中止して通知します。 | 形式が正しければ取り込み、違っていれば処理を中止して通知します。 | 二つの分岐が追えるので残す。正しい形式の場合にも中止や通知を適用する文へ変えない。 |

### 原則 14: Markdownの太字が表示される書き方

Markdownとして表示される文章（GitHub、技術記事など）で太字を残すときは、太字として正しく表示される書き方にする。
CommonMarkやGitHub Flavored Markdownなどの構文規則では、`**` のすぐ内側が記号（「」『』（）【】、。やバッククォート等）で、すぐ外側が文字（ひらがな・漢字・英数字）である場合、太字として解釈されず、`**` がそのまま表示されることがある。実際の表示は処理系や表示先によって違い、矢印「→」のような記号に接する太字は、表示先によっては崩れない。yomiyasu の検査は確認した範囲の構文だけを扱う限定的な検査で、完全なレンダラーではない。見直し候補が0件でも、あらゆる環境での表示や、文章の自然さ、意味の保持を保証しない。

太字を残すときは、次の優先順で直す。
1. かっこごと太字にしているときは、かっこの内側だけを太字にする。
2. 太字の終わりが句点などのときは、句点を太字の外に出す。
3. 1と2ができないとき（コードで始まる・終わる太字、かっこが2つ以上ある太字など）は、`**` の外側の、文字に接する側に半角スペースを1つ入れる。この半角スペースは太字を表示させるための区切りであり、消さずに維持する。

元の文で太字にならない書き方になっている箇所は、太字を残すなら、ほかに直す箇所がない文でも同様に直す。意味は変わらないため「変えたところ」には書かない。修正案が不確かなときはそのまま当てず、太字の範囲や前後の文が崩れないかを確かめて目で整える。なお、太字を増やす規則ではなく、太字を減らす規則（domains/tech.md等）はそのまま維持する。

| 表示されない書き方 | 表示される書き方 | 直し方 |
|---|---|---|
| `次に**「文書の立場」**を決めます。` | `次に「**文書の立場**」を決めます。` | かっこの内側だけを太字にする |
| `これは**必須です。**詳しくは下に書きます。` | `これは**必須です**。詳しくは下に書きます。` | 句点を太字の外に出す |
| `立場は**「勧め」か「決まり」**で決めます。` | `立場は **「勧め」か「決まり」** で決めます。` | `**` の外側の文字に接する側に半角スペースを1つ入れる |

### 原則 15: 案内用の見出し

記事・文書・スライドの見出しは、新しく書く場合も推敲する場合も、その箇所で何を扱うかが分かる短い項目名にする。「保存期間」「削除後の復元」「共有できる期間」のような名詞句や、「材料を量る」のような短い動作を基本とし、語り出しや理由、操作の細部、警告・条件・結論を文のまま見出しに詰め込まない。長い文の見出しにしない。
記録先や場面が内容を見分ける手がかりになる場合は、本文にある具体的な語を見出しに残す。「記録」「引き継ぎ」だけに縮めず、「Issueに残す採用理由」「担当交代時の引き継ぎ」のように書く。
見出しから外した警告・条件・結論や、「先に」「全部」「ぬるま湯で」のような範囲・順序・手段、「思い切って」「意外と効いた」のような書き手の評価や態度は省かず、本文になければ本文へ移して同じ意味で残す。タイトルや導入が「3つの工夫」のように数を示し、見出しの番号がその対応を示している場合は、番号を残す。
見出しだけで警告や結論を伝えることが依頼で明示された場合に限り、その内容を見出しに保つ。警告や条件を含むことだけを理由に長い文の見出しを残さず、すべての見出しを名詞句にそろえることもしない。
発表の締めに置かれていることだけでは、見出しが結論を言い切る役割だとは決めない。本文の話題を案内する見出しなら、最後の見出しも同じ基準で整える。
「uvとは：仕組みと使い方」のように、「〜とは」とコロンで扱う話題をつないだ見出しは、コロンの後の語句を落とさずに「uvの仕組みと使い方」のような名詞句にする。「議事録：10月定例会」のように、文書の種類と対象を区切るラベルのコロンは残す。
紹介記事・宣伝文の見出しのキャッチコピー（「昭和から愛される〜」のような言い回し）は、短い項目名にせずに残す（doc-types/promo.md）。
議事録を推敲するときは、見出しを短い項目名に直さず、原文の見出しのまま残す（domains/business.md 3章。資料から新しく作るときは、この原則で話題ごとの項目名にしてよい）。

### 原則 16: コピー調の抑制

この原則で整える対象は、不要な読点で間を作る表現や、助詞句・副詞句で切るコピー調、評価の語だけの短い文を並べる型である。その型がない自然な文は、この原則のために言い換えない。
コピー調になっている実務文の本文は、文脈から確定した動作・判断・評価を、その文の働きに合う述語まで書く。自分で書く変更理由や補足説明にも、この型を持ち込まない。型を整えるときも、原文と提供文脈で確定している対象の範囲・動作主・条件・手段を省かない。コピー調の見出しやスライドの見出しは、「保存先の指定」のように、その箇所の話題や手順が分かる短い語句にする（原則15。紹介記事・宣伝文の見出しを除く。doc-types/promo.md）。本文にある複数の担当者の動作を、一つの担当者の動作にまとめない。
「資料を、全員へ。」「作業を、もっと確かに。」のように、短い句の後で間を置き、助詞句や副詞句で切るコピー調は使わない。原文にある同じ型も、意味・比重・文の働きを保った表現に整える。読点だけを消して同じコピー調を残したり、語尾を散らすためにこの型へ変えたりしない。
意味を取り違えるおそれがなく、主語・目的語から述語へ続けて読める箇所は、助詞の後で区切らず一続きに書く。「資料を確認します」「担当者が更新しました」のような文に、間を作る読点を新たに足さない。条件・逆接や長い句を読み分ける読点は、助詞の後にあるという位置だけで削らない。
「速い。軽い。安い。」のように、評価の語だけの短い文を並べてリズムを作る型は、何を評価しているかが原文や前後の文から確定する場合に、対象と評価を述語までつないで書く（前の文で紹介したツールの評価なら「このツールは速く、軽く、安い。」）。評価の語を足したり減らしたり強めたりせず、元にない理由・逆接・比較も足さない。評価の対象が確定しない場合は、対象を作らずに原文を残す。小説や随筆の語りや会話で、書き手が文体として短い文を重ねている箇所と、紹介記事・宣伝文の本文で評価の語を短く重ねて勢いを出している箇所は残す（doc-types/promo.md）。
動作や意図を原文・提供文脈から確定できない場合は、型を消すために具体的な述語や効果を作らず、output-format.md 6章の暫定文の書き方に従う。原文の引用、確認項目の名称などの用途上十分な省略は保つ。
