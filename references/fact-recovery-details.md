# 「事実の確かめ」の細部

`references/fact-recovery.md` から、当てはまるときだけ読む。章の番号は fact-recovery.md の続き。例はすべて合成で、harune-backup とミナモ商事は架空の名前。

## 5. 問いの形と例

問いのまとまりは、元の書き手（人か別の AI）にそのまま貼って渡せる形にする。

1. 冒頭に次の文を置く: 「次の文章について、足りない事実を教えてください。分からないものは「分からない」と書き、推測で埋めないでください。答えの元にした資料や記録があれば、その名前と場所も書いてください。」
2. 各問いに、原稿の文をそのまま引用し、場所（何段落目、何行目、見出しの名前）を添える。
3. 何が足りないかを、事実の種類（数値と単位、日付、人か部署、条件、変わる前と後）で尋ねる。候補の値を挙げない。
4. 前提を置かない（元にない名前や値を前提にした「担当は田中さんですか」のような問いにしない）。
5. 原稿の文だけを引用する。材料や会話から知った値と社内の情報（決まっていない予定、会話のメモの中身、設定のキーや値、ログの名前と中身、子エージェントや自分の推測）は書かない。原稿にない事実を足してよいかを尋ねる問いも入れない（受け取るのが外部の AI のことがある）。
6. yomiyasu の語（事実の穴、check、材料）を使わない。好みの問い（この比喩を残すか）を入れない。
7. 意図してぼかした所を問うときは「書かない理由があれば、そのままにします」と添える。
8. 3つまで。選ぶ順は、読み手が動けない所、見出しと最初の段落、同じ文書で何度も出る所。残りは「ほかに N か所」と1行で添える。
9. コードの囲みに入れない。

例（利用者が別の AI の出力として貼った文章で、会話にも資料にも料金の話はない）。

> 新しい料金体系により、多くの利用者にとってより柔軟な選択肢が生まれます。移行は段階的に進め、混乱を最小限に抑えます。

```markdown
### 事実の確かめ
- 照らした材料: なし（文章だけを受け取ったため）
- 確かめられなかった点: 次の2点

#### 元の書き手に渡す問い

次の文章について、足りない事実を教えてください。分からないものは「分からない」と書き、推測で埋めないでください。答えの元にした資料や記録があれば、その名前と場所も書いてください。

1. 「新しい料金体系により、多くの利用者にとってより柔軟な選択肢が生まれます。」（1段落目）
   料金体系の何が、どう変わりますか。変わる前と後を書いてください。
2. 「移行は段階的に進め、混乱を最小限に抑えます。」（1段落目）
   移行はいつから、どの順に進めますか。日付と、対象になる利用者の範囲を書いてください。利用者がすること（手続きと期限）があれば、それも書いてください。
```

本文は1章の規則で直すだけで、値は1つも足さない。「多くの利用者」のようなぼかした語は、読み手が誤って読む恐れがないので問わない。

文脈がある例。この会話で AI が harune-backup のリリースノートを書き、そのあと利用者が「保存は30日、削除は毎日3時に走ります」「古い設定のままだと、判定に影響が出るかもしれない。確かめていない」と書いた。会話に出た `git diff` の出力では、すべての環境で読む `harune/retry.py` の `RETRY_INTERVAL_SECONDS` だけが変わった。原稿の「再試行の間隔を短くしました。」「毎日2時に削除されます。」「判定が誤動作します。」は、次のようになる。

```markdown
### 事実の確かめ
- 照らした材料: この会話の利用者の発言、git diff の出力（harune/retry.py）
- 補った: 「1秒から0.5秒に」← git diff の出力（harune/retry.py）「-RETRY_INTERVAL_SECONDS = 1.0」「+RETRY_INTERVAL_SECONDS = 0.5」
- 直した: 「毎日3時に」（原稿は2時。出典なし）← 利用者の発言「削除は毎日3時に走ります」
- 直した: 「影響が出るかもしれません」（原稿は「誤動作します」と言い切り）← 利用者の発言「判定に影響が出るかもしれない。確かめていない」
- 材料と合った値: 30日（照らしていない値と主張があります）
- 確かめられなかった点: 次の1点

#### 元の書き手に渡す問い

次の文章について、足りない事実を教えてください。分からないものは「分からない」と書き、推測で埋めないでください。答えの元にした資料や記録があれば、その名前と場所も書いてください。

1. 「古い設定のままの環境」（3行目）
   どの設定が、どの値のままの環境を指しますか。
```

「まだ確かめていません」は本文に足さない（補うために新しい文を作らない）。この例の check の照合の節には「資料にあった確度の語が最終稿にない: 確かめていない」が値を添えずに出るが、3行目の確度は資料の「かもしれない」と同じなので、そのままでよい。

## 6. 種類と宛先、意図した省略

種類ごとの扱い。

| 種類 | 会話やファイルから補うか | 問い |
|---|---|---|
| pr、article、incident、proposal、minutes、manual、slides | する | 返す |
| mail | する。宛先が社外なら下の表の社外の列 | 返す |
| paper、formal | しない | 文脈にない穴だけ返す |
| promo | しない | 新しい問いは出さない。根拠のない誇張だけを doc-types/promo.md 2章どおり「書き手に確かめたい点」で尋ねる |
| essay | しない | 出さない |
| 種類を決めない | する。宛先は分からないものとして社外の列 | 返す |

- promo、formal、paper で文脈に中身がある穴は問わない。本文は変えず、「補える事実（本文には入れていません）: 値 ← 出典」と1行で書く。
- 書き直す前に1回だけ確かめる問い（SKILL.md Step 1）に、事実の問いを混ぜない。事実の問いは書き直したあとの返答に付ける。

入れてはいけない事実（出典があっても、本文にも問いにも入れない）。

| 種類 | 社内向けと分かる | 社外向け、または分からない |
|---|---|---|
| 認証情報（パスワード、API キー、トークン、接続文字列、秘密鍵） | 入れない | 入れない |
| 個人の情報（名前、メールアドレス、電話番号、利用者 ID） | 原文にある名前を、材料が同じ役割で名指しているときだけ。原文にない名前は足さない（議事録の発言者の行にも） | 入れない |
| 社内の構成（内部のホスト名、IP アドレス、サーバーのパス、社内の URL、チケット番号） | 原文に同じ種類のものがすでにあるときだけ | 入れない |
| 未公開の数値と予定（売上、費用、顧客数、価格、発売日、影響件数） | 原文に同じ種類の値があり、原文の文がその値を求めていて、ぼかした書き方がないときだけ | 入れない。ただし問いに答えた値には、この行を当てない |
| 取引先と顧客の名前 | 原文に取引先の名前がすでにあるときだけ | 入れない |
| セキュリティの細部（再現手順、設定の弱点） | 原文に同じ種類のものがあるときだけ | 入れない |
| リポジトリの中の名前（ファイル名、関数名、設定のキー、エラーの番号） | 入れてよい | 原文が同じリポジトリの名前を出しているときだけ |

- 宛先は、依頼の行き先（「お客さまへのお知らせ」「社内 Wiki」）、種類、読者の順で決める。決まらなければ社外の列を使う。PR 説明は、依頼に「社内」とない限り分からないものとして扱う。
- 入れなかったときは、本文を原文の書き方のまま残す。読み手が動くのにその事実が要るときだけ、値を書かずに「資料には担当者の名前がありますが、社外向けと判断して本文には入れていません」と知らせる。

書き手が意図して省いたことをうかがわせる手がかりは次のとおり。どれかがあれば、その箇所は補わず、問いも出さない。

- 利用者が会話で省くよう言った（「取引先の名前は出さないでください」「数字はぼかしておいて」）。
- 原文が省いたことを示す（「詳細は省きます」「別途お知らせします」「（社外秘）」）。
- 数、時期、相手をぼかした語（「一部の利用者」「近日中に」「ある取引先」）。
- 依頼が要約か短くすることを求める。読者に合わせて細部を落とした文書（読者が general で技術の細部がない）。
- 書き手が決めていないことを示す（「未定」「調整中」）。
- 推敲する側が、わざとぼかした書き方かもしれないと思った（上の手がかりがなくても。利用者が自分の言葉で答えた値には当てない）。

例外は、ぼかした語のせいで読み手が誤って読む恐れがある（期限があるのにないと読める）ときだけで、「書かない理由があれば、そのままにします」と添えて1回問う。

## 7. 穴の種類の細部

| 穴 | 例 | 行うこと |
|---|---|---|
| 比喩、擬人化、誇張で中身が見えない | 「この失敗の連鎖を断ち切ります」「復元が大幅に速くなりました」 | 原文の前後か材料に中身があれば書く。なければ SKILL.md 1章のとおり言い換えるか残し、読み手が動けない所だけ問う |
| 文に要る要素の抜け | 「再試行の間隔を短くしました」の「何秒から何秒に」 | 材料に同じ主張の文があれば補う。なければ問う |
| 自分が書いた原稿の値か主張に出典がない | 「毎日2時に削除」が会話にも資料にもない。AI が会話で「おそらくディスクの空き不足」と推測しただけの原因が、原稿では「原因はディスクの空き不足でした」と言い切りになっている | 値は、材料の値が1つに決まれば訂正、なければ問う。主張は本文を変えず、「確かめた結果ですか。記録があれば場所を書いてください」と問う |

- 比喩の中身として材料の事実を書いてよいのは、原稿そのものが中身を指している（すぐあとの箇条がその出来事を説明している）か、材料に同じ文脈で同じことを述べた文があるときだけ。どちらでもない比喩（「運用を支える土台づくりです」）に、材料のどこかにある別の事実（将来の計画など）を当てはめない。
- 中身のない比喩を問いに置き換えない。根拠がなければ SKILL.md 1章の「比喩動詞の具体化」のとおり、何がどう変わったかを書くか、ふだんの言い方を選ぶ。
- 結びの決意や抱負を、材料にある具体策で埋めない。
- 言い直しテストとの関係は fact-recovery.md 3章。SKILL.md の言い直しテストの文は、その読み方で当てる。

## 8. check への渡し方と出力の見方の細部

区切りの行は、行全体を次の形で書く。

- `<<<yomiyasu:material 出典>>>`（出典は省いてよい。200字まで、`>>>` を含めない）。
- `--material` のファイルの、空白でない最初の行が区切りの行なら、区切りごとに別の資料になる。そうでなければ、ファイル全体が1つの資料になる。
- `<<<yomiyasu:` で始まるほかの行（`<<<yomiyasu:materials>>>` のような書き損じ）があれば、check は終了コード2で止まり、何も記録しない。正しい形に直して実行し直す。
- 出典は記録に残るが、照合しない（出典の中の数は、資料の値として照らされない）。根拠の行頭に `[利用者の発言]` のような札を書かない。札の中の数が資料の値として照らされる。

ファイルを作らない対話では、抜き書きを `run --stdin` の material の部分に書き、修正後の run にも同じ文を写す。

```bash
python3 <スキル配置ディレクトリ>/scripts/yomiyasu_check.py run --stdin --fact-gaps <<'YOMIYASU_EOF'
<<<yomiyasu:original>>>
（原文）
<<<yomiyasu:material 利用者の発言>>>
保存は30日、削除は毎日3時に走ります
<<<yomiyasu:final>>>
（最終稿）
YOMIYASU_EOF
```

照合の節（■ 資料との照合）の行の読み方。

- 「資料に基づく補足の候補（該当行）」: 値と、資料の何行目にあったか。
- 「単位のない数とだけ一致」: 最終稿の値（0.5秒）と同じ数が、資料に `名前 = 数` か `名前: 数` の形の行（`+RETRY_INTERVAL_SECONDS = 0.5`）にだけある。「資料にない数値」に数えたまま、行を見せている。根拠であることは示さない。`retry_wait = 3` を回数の「3回」に使う取り違えもここに出るので、行の名前と最終稿の文を読み比べる。
- 「資料にあった確度の語が最終稿にない」に値が添えてあれば（「予定（30日の文）」）、その値の文の確度を資料に合わせる。値が添えていなければ、どの文の語かを資料と最終稿で読み比べ、補った文や直した文の確度が資料と同じなら、そのままでよい。行を消すために新しい文を作らない。
- 事実の穴の候補の節（■ 事実の穴の候補）は、比喩、程度の語、前後の値のない変化、効果だけの文の一部を拾う。候補にない穴もある。essay と promo では出ない。formal と paper では、見出しの文が「この種類では補わず、必要なら書き手への問いにしてください」になる。候補は `--fail-on` に数えない。
- 抜き書きも記録（`.yomiyasu/inputs/`）に写しが残る。記録を残さないよう頼まれたら `--no-record` を付ける。
- check は抜き書きがファイルや出力と同じかを確かめない。抜き書きを作らない、言い換えない。
- 正しく補った値でも「元にない数値」として出る（資料に合わせて確度を強めた訂正も「確度が強まった」として出る）ので、`--fail-on=meaning-risk` を付けた実行は終了コード1になる。

## 9. ほかの場面

| 場面 | 補う・直す | 問い | 「事実の確かめ」 |
|---|---|---|---|
| 文章だけ（会話にその話題がない、一回きりの実行で材料がない） | しない | 読み手が動けない所だけ | 「照らした材料: なし」 |
| すでに自然な原稿（自分が書いた原稿でないもの） | 穴がなければしない | 出さない | 出さない |
| 本文だけを返す指定 | 会話やファイルからはしない（渡された資料での訂正は今のまま） | 出さない | 付けない。本文の前後に注記も付けない |
| 利用者が「確かめずに」「事実は確かめなくていい」 | 本文だけの指定と同じ | 出さない | 付けない |
| 利用者が「質問しないで」 | する | 出さない | 補った分だけ |
| Python を実行できない | しない（照合の見張りがない） | 返す | 「照らした材料」まで書いてよい |
| ほかのスキルの途中（PR を作るなど） | する | 返答に付ける | 返答に付け、PR 本文には節、出典の注記、問いを入れない。提出は verify のあと |
| 子エージェントで、呼んだ側の会話が見えない | 依頼に書かれた材料からだけ | 呼んだ側の AI へ返す | 付ける |
| 一回きりの実行（`claude -p`、`codex exec`、CI） | する | 報告に付けて返すだけ（待たない） | 付ける |
| 長い会話で前半がまとめられた | まとめの中の文は使わない。引かれた元を開き直せたときだけ使う | 返す | 付ける |

答えが返ってきたとき（新しい依頼）。

- 最終稿は新しいファイル名で保存し、check の run に `--new-run` を付けて新しい実行にする（保存名を変えるだけでは、前の実行につながることがある）。`--source` には最初の原稿を渡す（1回目の最終稿を渡すと、1回目に補った値が原文の値になる）。1回目に補った値は、根拠の行を新しい抜き書きに入れ直し、入れられなければ戻す。
- 利用者が自分の言葉で書いた答えは、利用者の発言として確度を変えずに使う（「たぶん」は「たぶん」、言い切りは言い切り）。「分からない」は補わない。
- AI が書いた答え（別の AI の答えを貼ったもの、yomiyasu を呼んだ AI の答え）と、書き手の分からない答えは、出典（ファイルと行、記録、利用者の発言）が書かれた行だけを使う。ほかは「答えにあったが、出典の記載がないので入れていない点」に並べる。利用者が「この値で入れて」と言えば、利用者の発言として使う。
- 答えた問いを聞き直さない。答えの中身についても問わない。新しく問うのは、元の原稿の穴のうち、まだ尋ねていないものだけ。
- yomiyasu の側から催促しない。子エージェントとして呼ばれたときは前の往復を覚えていないので、往復が終わるのは、呼んだ側が元の原稿と、前の問いと答えをまとめて渡すときに限る。呼んだ側には、答えを区切りの行つきの抜き書き（`<<<yomiyasu:material 出典>>>`）で渡してもらい、出典が利用者の発言、ファイル、出力を指さない行は AI の発言として扱う。
